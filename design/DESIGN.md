# WorkPanda 设计契约

> 本文件定义 WorkPanda 面向群众的 Web/H5 体验、交互和组件设计约束，供产品、设计、工程及 AI coding 代理共同遵循。
>
> 本文件与具体框架、组件库、CSS 方案和品牌视觉无关。技术栈、品牌色、字体和具体设计令牌尚未确定；不得在实现中将临时选择描述为已批准的项目标准。

## 1. 设计目标与边界

WorkPanda 为群众提供自然语言公共服务入口。界面需要让用户清楚理解当前办理事项、系统状态、需要补充的信息、即将发生的动作以及可选择的后续路径。

设计目标：

- 降低群众寻找服务入口、理解流程和重复填写的成本。
- 支持口语、简称、错别字和不完整描述；信息不足时清楚、友好地澄清。
- 让办理状态、用户待办、关键动作和结果可见。
- 自动化失败时诚实说明，并允许用户继续尝试、恢复任务或转人工。
- 在 Web/H5 和未来桌面端保持一致的业务语义、状态和确认含义；端侧差异仅用于适配交互方式。

界面不能取代业务控制：

- 业务规则、流程状态、权限、参数校验和工具授权由服务端负责。
- 隐藏、禁用或重新命名按钮不能代替服务端授权。
- 提示词、文案、视觉层级或用户点击不能代替服务端对关键操作的确认校验。
- 不得让模型决定政策、自由改变流程或编造办理结果。
- 不索取或代持密码、短信验证码、人脸信息、支付凭证等强认证信息；需要时引导群众在官方页面自行完成。

## 2. 设计原则

1. **状态清楚。** 用户应能辨认系统已收到请求、正在处理、等待用户输入、执行中、结果待确认或已完成。
2. **下一步明确。** 除终态页面外，应说明用户现在可以或需要做什么。
3. **逐步澄清。** 优先一次询问一个关键缺失信息；只有确实需要比较选择时才同时展示多个选项。
4. **关键动作可理解。** 执行提交、发送、修改等动作前，展示动作对象、关键字段和可能影响，并给出明确确认或返回修改的选项。
5. **失败诚实可恢复。** 说明已完成内容、失败环节和下一步选择；无法验证外部结果时，明确显示“状态待确认”。
6. **用户始终有控制权。** 允许取消、补充、更正、恢复或转人工；取消无法撤销已发生的外部副作用时，必须明确说明。
7. **最小化数据暴露。** 只展示当前任务需要的信息；默认遮蔽不需要再次查看的敏感字段，不把敏感数据放入 URL、调试文案或示例内容。
8. **使用群众语言。** 不要求用户理解 Agent、Harness、Workflow、Runtime 等内部技术术语。
9. **一致而不僵化。** 共用组件保持含义和行为一致；必要的平台适配不能改变业务状态和确认语义。
10. **先可用，再装饰。** 视觉风格不能妨碍可读性、键盘操作、移动端使用或错误恢复。

## 3. 状态与流程呈现

### 3.1 统一状态语义

界面应能表达下列状态。实际状态名称由应用实现决定，但展示含义必须一致：

| 状态 | 用户应理解的含义 | 交互要求 |
|---|---|---|
| 空闲 | 可以开始描述需求 | 提供清晰入口和必要输入提示 |
| 已接收 | 请求已收到 | 及时显示确认，不让用户重复发送 |
| 正在识别 | 系统正在理解需求 | 提供轻量、真实的进度反馈；不能假报业务执行 |
| 需要澄清 | 缺少信息或存在歧义 | 指明需要补充的内容；未满足前不得暗示已开始有副作用的办理 |
| 等待用户输入 | 当前步骤由用户补充信息 | 保留上下文，标明需要填写的字段 |
| 等待确认 | 即将执行重要动作 | 展示摘要、影响和明确的确认/返回操作；不得默认确认 |
| 执行中 | 后端正在执行获准步骤 | 显示当前进度；避免重复触发同一动作 |
| 需要用户操作 | 用户需在官方页面或设备上自行操作 | 说明操作目标，不索取凭证，并提供“我已完成”等继续方式 |
| 已完成 | 结果已由可靠来源验证 | 显示结果、来源或后续指引；不得仅凭模型生成内容判定完成 |
| 失败 | 当前步骤未能完成 | 说明可确认的事实、失败位置和恢复选项 |
| 状态待确认 | 外部操作结果目前无法验证 | 不显示为成功或普通失败；禁止盲目重复提交，给出查询或转人工路径 |
| 转人工 | 自动化交由人工继续 | 说明交接状态；仅在获授权且用户知情的情况下传递必要摘要 |
| 已取消 | 用户取消了尚可取消的任务 | 说明取消范围；若已有副作用，分别说明其状态 |
| 断线/重连中 | 连接中断，任务可能仍在继续 | 显示连接状态和恢复方式；重连后从服务端权威任务状态恢复 |

状态文案必须对应真实服务端状态。前端不得根据动画结束、请求超时或模型回复推断任务已完成。

### 3.2 所有流程状态都要有定义

新增群众侧流程或重要交互时，必须定义：

- 正常路径和每个用户可见状态；
- 加载、空、失败、离线、超时和结果未知时的呈现；
- 用户可以执行的动作及明确禁止的动作；
- 返回、取消、重复点击和恢复会话时的行为；
- 哪些步骤可能产生外部副作用，以及确认发生在哪里；
- 成功结果由什么可信依据确认；
- 转人工时用户会看到什么、哪些信息会被传递。

不得只交付理想路径的页面，不定义错误和恢复方式。

### 3.3 进度与长任务

- 进度反馈必须真实反映服务端可验证的阶段，不得制造虚假的百分比或倒计时。
- 对无法估算时长的任务，说明正在处理的阶段，而不是编造完成时间。
- 长任务应显示任务仍在进行、用户是否需要操作，以及如何离开后恢复。
- 事件暂时中断时，应显示连接状态；恢复后从服务端任务状态同步，不能从本地动画续播并假装实时。

## 4. 通用组件契约

具体组件库未确定。实现时优先采用所选平台的语义化原生控件和项目已有组件；新组件应说明复用理由，并保持本节要求。

### 4.1 交互组件状态

按钮、输入框、选项、对话消息和状态面板等交互组件，按适用性明确以下状态：

- 默认、悬停、键盘焦点、按下；
- 禁用、提交中或等待响应；
- 成功、错误、警告和信息提示；
- 空内容、长内容、窄屏和放大文本；
- 离线、断线重连或服务不可用；
- 键盘与屏幕阅读器交互。

状态变化不得只靠颜色表达。视觉状态、辅助技术语义和可操作行为应一致。

### 4.2 按钮与动作

- 每个视图应有清晰的主要动作，避免多个同等突出且互相竞争的主操作。
- 文案应描述动作，例如“确认提交”“继续补充”“取消办理”“转人工”，避免含义不清的“确定”“好的”。
- 请求处理中应防止重复触发；同时由服务端保证副作用的幂等或重复请求保护。
- 危险、不可逆或会产生重要影响的动作需明确说明影响，并按业务规则要求确认。
- 禁用状态应有可理解的原因或恢复路径；不可只用低对比度暗示禁用。

### 4.3 表单与澄清

- 每个输入控件必须有程序可识别的标签；占位符不能代替标签。
- 标明必填项、格式要求、可接受示例和错误修正方式。
- 输入错误应靠近对应字段展示，并与字段建立辅助技术可识别的关联。
- 校验错误后保留用户已经填写的非敏感内容；不要无故清空表单。
- 一次优先询问一个关键缺失信息；若提供选项，应确保选项互斥、含义清楚且覆盖必要情况。
- 只收集当前事项所需的信息。不得因界面方便而额外收集敏感字段。
- 确认页面应让用户检查和返回修改信息；重要提交前展示必要字段摘要。

### 4.4 对话与消息

- 清晰区分用户输入、系统状态、已验证结果和需要用户采取的操作。
- 识别、澄清、运行、等待确认和失败等状态不能只通过聊天气泡颜色区分。
- 消息内容应可读、可复制（适用时），长文本应有清晰层级。
- 对话滚动不能强迫用户在阅读历史时跳回底部；新消息到达时应以可感知但不打断的方式提示。
- 刷新或重连后应以服务端状态恢复任务，避免把过期对话状态展示为当前状态。
- 不将模型推理过程、隐藏提示、密钥、内部堆栈或不适合用户阅读的工具输出展示给群众。

### 4.5 确认摘要

对于提交申请、发送材料、修改数据等重要动作：

- 明确写出即将执行的动作及其目标对象；
- 展示足以发现错误的关键字段和影响；
- 提供明确的确认和返回修改路径；
- 不预先勾选确认，不用模糊的继续按钮代替确认；
- 用户确认后，前端只发送确认意图；后端仍须验证用户、任务、流程版本、参数摘要和一次性凭证；
- 超时、参数变化、任务状态变化或凭证失效后，应重新确认；
- 界面确认不能替代服务端权限检查，也不能允许通过重复点击重复执行。

### 4.6 错误、待确认与人工转接

用户可见的失败说明应包含：

1. 当前可以确认发生了什么；
2. 哪些步骤已完成，哪些未完成或结果未知；
3. 用户可以采取的下一步；
4. 在适用时如何重试、查询、恢复或转人工。

不得显示内部错误堆栈、密钥、敏感日志或未经验证的原因。对结果未知的外部操作，应突出“状态待确认”，并优先提供官方查询或人工确认，不显示可直接重复提交的主按钮。

人工转接应：

- 说明自动化将交由人工继续；
- 提供人工渠道、可用时间和预期等待信息（仅在业务方确认后展示）；
- 仅传递经过授权且继续办理所需的最少信息；
- 让用户知道哪些信息会被转交，并在需要时取得同意；
- 在渠道不可用时如实说明并给出可行替代方式。

## 5. 内容与文案

- 先说明当前状态或结论，再说明原因和下一步。
- 使用短句、常用词和群众熟悉的业务称呼；一次尽量表达一个任务。
- 重要动作使用明确动词；错误文案要给出可执行的恢复路径。
- 不把系统内部状态说成业务办理结果。
- 未确认外部结果时使用“状态待确认”或同等明确表达；不得称为“已办理成功”。
- 用户自行操作时，讲清操作目标和如何返回，不索取密码、短信验证码、人脸或支付信息。
- 不向群众展示 Agent、Harness、Runtime、Workflow、API、DOM、超时堆栈等内部术语；确有必要时用用户可理解的解释。
- 文案不能保证未经业务方确认的政策、办理时限、资格或结果。
- 同一状态和动作在不同页面、渠道中使用一致术语。

示例：

- 澄清：“我理解您想查询办理进度。请问您要查询哪一项业务？可以选择社保、医保或住房公积金。”
- 自动化失败：“这个页面暂时无法稳定完成操作，我没有提交信息。您可以转人工继续办理，或稍后再试。”
- 结果待确认：“提交结果暂时无法确认。为避免重复办理，请先查询办理状态，或转人工核实。”

实际业务话术须由业务方审核；示例不是政策承诺。

## 6. 响应式与多端适配

首期面向响应式 Web/H5，并覆盖手机、平板和桌面浏览器。桌面客户端不是首期必需品。

- 窄屏下优先保留状态、主要内容和主要动作；不要要求横向滚动才能完成核心任务。
- 页面缩放和大字号下，信息与操作仍须可读、可达；不通过裁切隐藏重要内容。
- 长字段、长错误、长按钮文案和多选项必须有稳定布局，不得覆盖相邻内容。
- 不依赖悬停、拖拽或复杂手势完成核心操作。
- 桌面布局可利用更宽空间，但不得改变状态机、权限和确认语义。
- 若未来采用 PWA 或桌面壳，离线提示、窗口缩放、键盘操作和恢复行为须单独验证；不得默认假设桌面客户端存在。

具体断点和布局 token 应在实现框架确定、页面原型验证后形成，不在当前框架无关规范中臆定数值。

## 7. 无障碍基线

以 WCAG 2.2 AA 作为设计目标。适用的规范性要求应结合最终技术方案和适用法规确认；本节不替代正式合规审计。

- 核心功能可通过键盘完成；焦点顺序符合阅读和操作顺序，焦点可见且不被遮挡。
- 使用语义正确的标题、区域、按钮、表单标签和状态信息。
- 动态状态更新应在不打断用户的前提下可被屏幕阅读器感知；避免频繁播报无关变化。
- 错误、必填、成功和警告状态不能只用颜色表达。
- 文本和控件应满足适用的对比度要求；信息图形和焦点指示也应清晰可辨。
- 支持放大文本和窄屏重排；避免缩放后内容或功能丢失。
- 触控目标应足够大且间距合理；若受平台或场景限制，应提供可访问的替代操作。
- 动画应简短且非必要；尊重减少动态效果偏好，不用动画表达唯一状态信息。
- 图片、图标按钮和图表应提供适当的替代文本或可访问名称；纯装饰内容不重复朗读。
- 颜色、图标和形状使用一致语义，并配有文字或辅助技术说明。

## 8. 设计令牌与视觉系统

当前未批准品牌视觉和前端技术方案，因此暂不规定具体色值、字体、断点、间距数值、圆角半径、阴影、动效时长或 UI 库。

视觉实现确定后，应集中管理并语义化命名令牌，至少覆盖：

- 文本、背景、表面、边框和焦点；
- 主要/次要/危险动作；
- 信息、成功、警告、错误和待确认状态；
- 字体族、字号、字重、行高；
- 间距、布局宽度、断点；
- 边框、圆角、阴影和动效。

组件应引用语义令牌，而不是散落硬编码值。新增例外应说明原因，不能仅因单个页面的视觉偏好而创建重复令牌。色彩不能单独承担状态含义。

## 9. AI coding 的 UI 工作流程

实现面向群众的 UI 前，编码代理必须：

1. 阅读本文件及相关需求、状态定义和现有组件；
2. 说明涉及的用户流程、页面状态、风险等级和待确认事项；
3. 对关键流程列出正常、错误、加载、离线和恢复路径；
4. 复用现有组件和设计令牌；没有现成组件时，先说明新建理由；
5. 按仓库实际具备的工具运行组件/集成/端到端测试，不得臆造命令；
6. 对视觉或响应式变更，在可用环境中检查移动和桌面视口、长文案及焦点行为；
7. 报告实际检查的状态、视口和未验证内容，不得声称未执行的视觉审查已通过。

组件或页面变更应尽量以状态驱动的方式实现。测试优先验证用户可观察行为和业务语义，不绑定易变的内部 DOM 结构。

## 10. 按风险分级的 UI 验收

### 低风险：展示和非关键文案

- 使用已有组件和语义令牌；
- 不出现明显重叠、裁切、溢出或不可读内容；
- 键盘焦点和窄屏布局未退化；
- 相关的组件检查通过。

### 中风险：表单、任务状态、登录态数据展示

- 加载、空、错误、重试、断线和恢复状态均有定义；
- 表单标签、校验、错误关联和数据保留行为可理解；
- 只展示当前任务需要的数据，敏感字段适当遮蔽；
- 移动端和桌面浏览器完成针对性验证；
- 用户能够理解任务状态和下一步。

### 高风险：确认提交、发送材料、修改业务数据或身份流程

- 展示动作对象、关键字段、影响和确认/返回路径；
- 服务端验证确认、权限、任务状态和参数；
- 重复点击、刷新、返回和断线不会重复执行不可幂等副作用；
- 未知结果明确呈现为待确认，不提供盲目重试；
- 转人工和停用/回滚路径可用；
- 业务/产品和技术责任人完成审查；
- 关键失败路径和负向行为有测试证据。

## 11. UI PR 检查清单

```text
[ ] 用户能辨认当前任务状态和下一步
[ ] 正常、加载、空、错误、离线、待确认和恢复状态按适用性均已定义
[ ] 关键操作的影响清楚，确认由服务端验证
[ ] 内部术语、堆栈、错误码和敏感值不会泄露给群众
[ ] 使用已有组件和设计令牌；新增例外有说明
[ ] 键盘可操作，焦点可见，语义和动态状态适用于辅助技术
[ ] 状态不只依靠颜色表达，文本和控件可读且不会重叠/裁切
[ ] 移动和桌面视口均按变更风险完成验证
[ ] 断线、刷新、返回、取消和重复触发行为按适用性已验证
[ ] PR 记录了测试/视觉检查证据和未验证项
[ ] 已判断问题是否应沉淀为组件、模式、令牌、测试或内容规范
```

## 12. 设计规范的复利维护

每次 UI 缺陷、用户困惑或重复返工，都应判断根因属于：

- 组件缺少状态或行为约束；
- 设计令牌缺失或含义不清；
- 页面/流程模式未定义；
- 内容文案或术语不清；
- 响应式或无障碍规则缺失；
- 用户研究或验收标准不足；
- 实现或测试没有遵循已有约束。

优先用组件测试、自动化检查、可复用模式或研究结论解决重复问题。只有跨任务稳定且可执行的规则才写入本文件。不得只追加“注意不要这样”的含糊提醒；应同时写明可观察的验收标准或对应控制措施。
