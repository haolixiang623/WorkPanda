## 判断留痕（可复用）

- **"结果未知"必须独立成一类结论**：超时既不能算成功也不能算失败，归档里标 `unknown`
  并置 `requires_manual_check`，否则运维会把它读成"没办成"，然后重复提交一次真实动作。
- **审计只存指纹不存参数**：审计文件要长期保留，写进原始参数等于给自己制造一份

- **留痕失败不得击穿执行**：归档写出异常时业务结论必须保持不变（有单测守卫）。
- **并发轮次仍在同一 worktree**：本轮全程在独立 worktree
  （`automation-.../wt-harness-audit`）+ 特性分支上开发，未触碰 worker 的未提交改动。

## 判断留痕（可复用）

- **取消 ≠ 失败 ≠ 超时**：三者都不能当成功，但取消要保留断点（人取消的是"继续跑"），
  超时要把断点标成不可续跑（外部可能已执行）。
- **不承诺"立刻停"**：同步工具线程杀不掉，硬杀等于把"是否已提交"变成未知；
  对外只说"不会再有新的动作"。
- **取消必须先于状态翻转下发**：状态改了但执行线程不知道，等于没取消。
- **同步执行会吃掉取消**：执行在事件循环里跑时，HTTP 取消请求要排队到执行结束，
  这个部署前提比代码本身更容易踩，已写进 docs 第 14 节。

## 判断留痕（第八轮新增）

- **「信号存在」不等于「信号能到得了」**：上一轮的取消测试都是同线程直接置位令牌，
  没有任何一条同时发出「执行中」和「HTTP 取消」两个请求。边界检查再完备，
  没有触发机会就等于没有功能。
- **状态翻转必须在信号送达之后**：多进程下界面显示「已取消」而另一个进程还在提交，
  比一次可重试的 503 危险得多；写失败要报错，不能吞掉。
- **读不到共享状态要 fail-closed**：与步骤租约「占用状态不明即拒绝」同源——

- **离环会引入新的写者竞争**：执行不再占住事件循环后，「迟到的结果覆盖取消」
  才第一次成为真实并发，必须同步补状态守卫；只做前半段等于把 bug 从「点了没反应」
  换成「取消又变回完成」。
- **剩余极窄窗口**：守卫读状态到结果持久化之间收到取消仍可能落一条迟到结果，
  彻底消除需要存储层条件写（compare-and-set），已写进文档第 16 节，未做。

## 判断留痕（第九轮新增）

- **「先判定、后写入」两步永远不是互斥**：只加一次状态守卫只能挡住读之前已发生的
  取消；真正的并发里对方可以在守卫返回之后动手。要互斥就得让判定与写入是同一个
  原子动作。
- **事件必须跟状态同生共死**：只给 `save` 加 `WHERE status = ?` 仍会留下「状态没
  写成、结果事件却先落了一条」的错位。所以原语是「状态 + 一批事件」的事务提交，
  不是条件更新单行。
- **双方都得用 CAS**：只改执行侧，取消方的无条件 `save` 照样能盖掉刚写出的完成；
  仲裁必须是共享协议，不是单边补丁。
- **条件写输了不是写失败**：语义是「另一个写者先赢了」，执行侧交回权威状态、
  取消侧报错让使用者刷新，都不重试覆盖。与租约「状态不明即拒绝」同源。
- **网络通道**：本机 GitHub API 走默认 / 7897 代理会稳定报 `SSL: UNEXPECTED_EOF`，
  用 `urllib` 的 `ProxyHandler({})` **直连**稳定可用；`git push` 同理要
  `-c http.proxy= -c https.proxy=` 直连。两者交替重试有效，无需换工具。

## 第十轮：暂停态也是承诺，一并纳入条件写（PR #23，`78cfb19`）

## 判断留痕（第十轮新增）

- **「耗时极短」不是不做原子写的理由**：并发窗口的宽度与写入耗时无关，只与
  「有没有人在同一时刻想改同一行」有关。取消恰好落在暂停那几毫秒里，一样写错。
- **中间态也需要定义「谁说了算」**：只要这条写入决定了任务接下来等谁，它就是一次
  承诺，必须和它的事件同生共死；只有纯过程事件（`STEP_STARTED`/`STEP_COMPLETED`）
  可以即时写。
- **旧快照当期望值是反模式**：CAS 的期望值必须来自**刚刚从库里读到的**状态，
  不能来自调用方手里的对象。否则「库里恰好没变」会让本该失败的条件写成功。
  终态要在入口处直接短路返回，而不是靠后续状态机兜。
- **删掉后门比改好三处更重要**：留着 `_persist` 这种无条件写助手，下一个切片很容易
  又用它；删掉后想让暂停写盘只有条件写一条路。
- **反向验证很划算**：把新用例 stash 掉源码再跑一遍，确认 5/6 失败，比盯着覆盖率
  更能说明「用例真的盯着这个缺陷」。
