## 事故：一次「半提交」差点把 #80 从 main 上抹掉（务必记住）

**现象**：在共享 main worktree 里 `git add .workbuddy/memory/2026-11-09.md` 然后 commit，
`git show --stat` 却显示 `README.md -21`、`runner.py -213`、`HARNESS.md -116`……
记忆文件只加了 347 行，改动却是 **22 个文件、1965 插入、471 删除**。

**根因**：共享 worktree 的 `git reset --soft <时点>` 挪了 HEAD，把**索引里残留的
全套已暂存改动**（#80 的全部源码、文档、前端）一起带进提交。`git add <单个文件>`
只更新这一个条目，**不会清掉索引里其他已暂存条目**。

**后果**：这个提交被 push 上 main（`e66df3e`），远端 main 上 #80 的 32 个文件
被整体回退成「#80 之前」，`tests/test_user_action.py` 被删除。随后我又用 GitHub API
以这个坏提交的树做 `base_tree` 打补丁，**把坏状态又复制了一遍**（`db4d6b65`）。

**修复**：API 重建提交，`parents` 显式指向合并点 `ecc0c2c`，`base_tree` 取合并点的树，
只加记忆文件 → `66b60c6c`。逐条核对：远端 main 与合并点**唯一差异**就是那个记忆文件，
其余 270 个条目 sha 全等。main 上重跑全量 1040 passed。

**教训（写进肌肉记忆）**：
1. 提交前**先看 `git status --short` 的完整输出**，再决定提交。看到一堆 `M ` 在暂存区
   就是信号——`git add <单文件>` 之后暂存区里**可能还有别人的/别的事的**内容。
2. **不用 `git reset --soft` 来「改上一条提交」**。要改就用 `git commit --amend`
   并显式传路径，或者干脆新开一个提交。
3. **push 前 `git show --stat HEAD` 数一遍文件数**。数字和预期不符就是有东西混进来了，
   这时还没推出去，撤销成本极低。
4. 用 GitHub API 打补丁时，`base_tree` **必须取「我想要的那个提交」的树**，
   不能取「当前远端头」的树——否则坏状态会被原样继承。
5. API 的 `/git/commits/<sha>` 需要**完整 40 位 sha**，传短 sha 返回 404（不是 422），
   容易被误读成「提交不存在」。
6. `git push` / `git fetch` 的 HTTPS 传输会整体挂掉（`Empty reply from server` /
   `SSL_ERROR_SYSCALL` / 75s 超时），但**同一时刻 `api.github.com` 走 `curl --http1.1`
   是通的**。传输层挂了就走 API 推（blob → tree → commit → PATCH ref），
   别在 git 上反复重试。
