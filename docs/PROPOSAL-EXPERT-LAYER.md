# 提案：「专家」层怎么设计（不含实现）

文档状态：**已审核接收（2026-11-09 19:00 UTC+8）**。
设计状态：**尚未拍板**——第 5 节的 D1–D4 仍待回答，本文不代表已批准的设计，也不含代码。
写作目的：把"群众页接真实专家 harness"这个诉求拆成能分别判断的几件事，避免直接
落成一个既不可验证、又容易被当成承诺的"人设"。

---

## 1. 现在的真实情况：系统里没有"专家"

不是没做，而是刻意没有这一层：

| 位置 | 现在是什么 |
|---|---|
| `harness/executor.py:default_step_prompt()` | 一句话自我描述——"你是受控执行器，只完成当前这一个步骤"，加执行要求、参数、可用工具清单 |
| 提示词里有没有领域知识 | 没有。人设、政策口径、FAQ、材料清单，一个字都没有 |
| 全仓"专家"字样 | 只出现在 Octop 控制台的 `/experts`——那是**运维助手**，面向运维排查，与群众侧无关 |
| `docs/OCTOP-INTEGRATION.md` §3.4 | 明确"不把完整流程定义、其他用户数据或历史会话交给运行时" |

所以群众问"我这个情况能不能办""要带什么材料"时，今天没有任何东西能回答——页面只会
按流程定义追问字段。这是设计缺口的诚实描述，不是 bug。

---

## 2. 先把"专家"拆成三件事

这三件事风险等级差得很远，混在一起谈必然谈不成：

**A. 办事一致性**（低风险，已经有一半）
同一事项、同样的材料要求，每次都必须一样。这属于**流程定义**，不属于模型——
`required_fields` + `field_labels` 就是它的载体。今天缺的只是"管理侧能把标签填进去"
（`docs/ISSUE-BACKLOG.md` A2）。这一项不需要任何模型能力。

**B. 解释与追问**（中风险，本文主张先做这个）
"这个事项是干什么的""需要带什么"，答案来自**政策原文/办事指南**，不是模型自己想。
关键约束是**可追溯**：每条答案都要能指向文件号与生效日期。

**C. 资格预判**（高风险，本文主张不做）
"我这个情况算不算就业困难人员"。这是行政裁量，模型给结论就是越权，而且群众会当真。
正确形态是"把判断依据讲清楚 + 指向窗口/电话"，不是给结论。

把 C 硬做成"专家"是这类系统最常见的失真点：做得越像专家，越像承诺。

---

## 3. 四种形态与取舍

| 形态 | 做什么 | 代价 | 结论 |
|---|---|---|---|
| **L0 现状** | 只有执行步骤提示词 | 群众问什么都答不了 | 保持，但明确写进验收口径，别再当成"专家已接入" |
| **L1 事项知识卡** | 知识条目随**流程版本**走，注入"解释性"环节 | 要有人提供并签字确认政策原文 | **建议先做这个** |
| **L2 检索式问答** | 接知识库，答案回链原文，前端展示出处 | 需要知识库、引用 UI、评测集 | 等 L1 跑顺再谈 |
| **L3 资格预判 / 代办** | 模型判断资格、代填代交 | 越权 + 无法核验 | **不做** |

L1 与 L2 的分界线：L1 的知识是**事项自带的一小段**（几十条），随版本发布、可被发布
门禁校验；L2 是**外部检索**，答案来源不在发布流程内，需要另一套"这条答案可信吗"
的机制。先做 L1 的理由是它天然可验证：知识条目改没改、谁批的、什么时候生效，全在
版本库里。

---

## 4. L1 的具体设计（待评审的最小切片）

### 4.1 数据放哪里

放在 **`FlowDefinition` 里**，成为版本内容的一部分：

- 理由与意图规则一致（D2=B）：知识若留在代码常量或独立可改的表里，"发布"就不再是
  一次生效，改口径可以绕过门禁；
- 版本不可变的规则照旧：改知识 = 发新版本，旧版本留档；
- 不新建"专家"实体。一个事项一个知识块，不是一个"专家"管多个事项——后者的授权
  边界说不清（谁能改这个专家的口径？影响哪些事项？）。

### 4.2 每条知识必须带的三样

| 字段 | 作用 | 缺了会怎样 |
|---|---|---|
| `answer` | 这段回答的事实内容 | 没有内容就没什么可注入 |
| `source` | 文件号/条文/办事指南名称 | 群众无法核对，运维无法回答"你凭什么这么说" |
| `effective_from` | 生效日期 | 政策换版后旧答案会一直生效，且没人发现 |

缺任一项**不允许发布**（409，与识别样例门禁同一形态：拦在发布口，不是运行时）。

### 4.3 注入到哪里（这条最要紧）

- **只注入面向群众的解释性文本**：澄清追问、转人工前的说明；
- **绝不注入 `EXECUTE` 步骤**。执行步骤的依据只能来自工具返回值——现行三态契约
  （`harness/contract.py`）里，`evidence` 空着就是 `unconfirmed`。知识块一旦进入
  执行步骤的提示词，模型会拿"我记得政策是这样"当依据，这条护栏就废了；
- 注入内容带明确边界："这些是可引用的口径，不是你自己的判断；超出范围就说不知道"。

### 4.4 硬约束（写进代码才有意义）

1. 知识不得改写 `instruction` / `required_fields` / `tool`——与现行"模型不得改写
   步骤意图"完全一致；
2. 知识不得作为执行依据（见 4.3）；
3. 答不上来必须**明说**并指向人工入口，不允许"兜圈子式回答"（模型最常见的失效）；
4. 每次回答的事实部分必须能追溯到某条知识条目；追溯不到就不该说。

### 4.5 为什么不做"人设表演"

语气、身份模拟（"我是您的专属就业顾问"）有两个问题：**不可核验**（没有任何断言能
证明它"像专家"），以及**容易被当成承诺**（自称顾问、又答错了，群众会认为这是官方
口径）。所以 L1 只用中性的功能性称谓（"办事助手"），把可信度放在"答案有出处"上，
而不是放在"说话像专家"上。

## 5. 需要拍板的四件事

| # | 决策 | 备选 | 影响 |
|---|---|---|---|
| D1 | 试点事项与知识来源 | 谁提供政策原文、谁签字确认口径？ | 没有签字人，L1 不该上线——知识错了比没有知识更糟 |
| D2 | 模型能否自由措辞 | ①允许措辞、禁止新增事实（建议）②逐字返回 | ①更像人话，但要靠"事实部分可追溯"来兜底 |
| D3 | 群众页是否显示出处 | ①显示并可展开原文（建议）②不显示 | ①增加页面复杂度，但这是唯一能让群众自己核对的方式 |
| D4 | 拿不准时的统一话术 | 转人工 / 留联系方式 / 提示去窗口 | 必须与"办不成怎么办"的整体设计一致，不能只在这层另定一套 |

D1 是硬前置：**知识条目没有签字人就不要上线**。

---

## 6. 明确不做

- 不做资格预判结论（C 类）；
- 不做"专家人设"表演；
- 不让知识进 `EXECUTE` 的 evidence 链；
- 不新建可独立编辑的知识表（会绕过发布门禁）；
- 不用 Octop 的 `/experts`：那是运维控制台，鉴权模型面向内部人员，与群众匿名会话不通。

---

## 7. 如果批准 L1：验收标准

必须能自动化的（回归）：

1. 知识条目缺 `source` 或 `effective_from` → 发布返回 409，且消息说明缺哪一项；
2. `EXECUTE` 步骤拼出的提示词里**不出现**任何知识条目（防止悄悄注入）；
3. 超范围提问 → 返回转人工话术，不含编造事实（用近似误例钉住）。

只能手工的：

4. 同一问题连问两次，事实部分一致、出处相同；
5. 拿一条已换版的政策，确认旧答案不再出现（验证 `effective_from` 真的生效）。

---

## 8. 与其它切片的关系

- **E2（第一个真实低风险事项）**决定知识条目的**内容**；L1 的**机制**可以晚于 E2。
  先跑通一件事的"收集→确认→执行→完成"，再给它加解释层，顺序不能反——否则会先
  争论"专家该说什么"，而流程本身还没验证过。
- **E4（副作用事项 + 真工具）**与本文正交：知识层不参与副作用。
- `docs/ISSUE-BACKLOG.md` 的 A2（管理侧补 `field_labels` / `intent_rules`）是 E2 的
  前置：不补，管理侧建出来的事项在群众页印内部字段名、且一句话命不中。

---

## 9. 结论

建议先按 **L1** 走，并把"知识条目必须带出处与生效日期、不得进入执行依据链"写成发布
门禁的一部分。这件事的价值不在"听起来像专家"，而在于**每句政策口径都能被追溯、
换版能被看见**——这恰好是当前系统最缺、也最容易在演示里被糊弄过去的地方。
