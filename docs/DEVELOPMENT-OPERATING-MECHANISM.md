# WorkPanda 开发运营机制

> 本文件把 `AGENTS.md` 和 `design/DESIGN.md` 中的工程约束落成可持续运行的开发机制。目标不是让 AI 无限制地自动写代码，而是让 AI 在已批准的边界内持续交付可验证的小切片，并把每轮反馈沉淀为下一轮的效率和质量提升。

## 1. 核心运行模型

```text
产品目标 → 可执行需求 → 风险分级 → 方案/设计评审
  → AI 隔离实现 → 自动验证 → 人工审查 → 测试环境
  → 小范围试点 → 运行/用户反馈 → 复盘与防回归 → 下一轮需求
```

人类负责业务目标、政策规则、风险承担和发布批准；AI 负责已批准任务的探索、实现、测试、文档和证据整理；CI 和运行系统负责自动验证、反馈和可追溯性。

## 2. 人机职责

### AI 可自动执行

- 阅读仓库规范、需求和相关代码；
- 分析任务并提出实现计划；
- 在隔离分支中实现低风险小切片；
- 增加测试、运行仓库已有检查、修复当前分支的 CI 问题；
- 生成草稿 PR、验证报告和复盘候选项；
- 将已确认的重复问题转成回归测试、脚本或改进任务。

### 必须由人确认

- 业务政策、首期事项、身份/实名策略和人工渠道；
- 流程步骤、工具白名单、权限模型和关键动作确认语义；
- 敏感数据、数据库迁移、认证方式和外部副作用；
- 生产发布、凭据变更、停用和事故处置；
- 高风险设计、业务规则和无法验证的结果。

AI 生成的代码不降低任何测试、审查、隐私或发布标准。

## 3. 任务生命周期

任务状态统一使用以下语义：

```text
候选 → 待确认 → 已批准 → AI 实现中 → 待验证 → 待人工审核
→ 待测试环境 → 试点中 → 已完成
```

异常状态必须区分：`需求不清`、`技术阻塞`、`测试失败`、`业务审核失败`、`安全审查失败`、`用户验证失败`。

### 任务进入 AI 队列的条件

低风险任务只有同时满足以下条件，才可标记为 `ai-eligible`：

- 用户问题、预期结果和非目标明确；
- 验收标准可观察、可验证；
- 修改范围和依赖明确；
- 风险等级已标注；
- 不涉及未批准的政策、权限、敏感数据或生产操作。

中风险任务需人工确认计划；高风险任务需先完成设计和责任人批准，不能由 AI 自行领取。

## 4. 标准 AI Coding 流程

1. **探索**：读取 `AGENTS.md`、相关设计/需求/架构、现有代码和测试；检查仓库实际可用的命令。
2. **计划**：列出目标、非目标、影响文件、风险、状态变化和验证计划。需求不清时先停下提问。
3. **实现**：一次只做一个完整垂直切片，不顺手重构无关代码；所有工作在隔离分支或 worktree 中完成。
4. **验证**：先跑最相关检查，再跑项目已有的完整检查；补充正常路径、失败路径和“不应发生”的负向测试。
5. **交付**：创建草稿 PR，记录变更、命令、结果、未验证事项、数据/权限影响和剩余风险。
6. **审核**：AI 审查只能补充，不能替代人工批准；高风险变更由对应业务/技术责任人审核。
7. **复盘**：把重复问题转为测试、CI、运行时保护、脚本、模板或明确的改进任务。

仓库没有技术栈或测试命令时，必须如实报告“尚未具备该项验证”，不得臆造命令或声称通过。

## 5. 风险与权限门禁

| 等级 | 示例 | AI 默认权限 | 必需门禁 |
|---|---|---|---|
| 低 | 展示、公开信息、非关键文案 | 可隔离实现并提草稿 PR | 自动检查 + 人工审查 |
| 中 | 表单、任务状态、会话、浏览器自动化 | 需批准计划 | 授权/隔离/失败/隐私测试 |
| 高 | 提交、发送、改业务数据、认证、权限、敏感数据 | 不自动领取 | 设计审查 + 业务/技术批准 + 负向测试 |

任何变更跨越多个等级，按较高等级处理。禁止 AI 访问生产凭据、生产数据或未经批准的外部服务。

## 6. WorkPanda 专用质量门禁

涉及业务流程或副作用的变更，至少验证：

- 缺参或歧义不会启动副作用；
- 工具只能调用当前流程节点白名单；
- 关键动作由服务端校验用户、任务、流程版本、参数摘要和一次性确认凭证；
- 重复请求不会造成不可幂等副作用；
- 外部结果未知时显示“状态待确认”，不得盲目重试；
- 超时、取消、断线、恢复和转人工不会产生虚假成功；
- 用户会话、浏览器 profile、日志和测试夹具相互隔离且不泄露敏感值。

涉及群众侧 UI 的变更，还必须遵循 `design/DESIGN.md` 的状态、无障碍、响应式和内容约束。

## 7. 分支、PR 与发布

- 主分支只接受通过 CI 和人工审核的 PR；
- 一个 PR 尽量对应一个可审查的行为变化；
- CI 失败优先修复，不能在不稳定基线上继续堆叠功能；
- PR 必须附准确的验证命令和结果，未运行的检查明确列出；
- 高风险功能先在测试环境或受限范围试点；
- 发布前确认人工转接、停用开关、监控和回滚路径可用；
- 发生越权、个人数据暴露、重复副作用或虚假成功时，立即停用受影响流程并启动事故处理。

在技术栈和部署链路确定前，不自动启用生产发布。

## 8. 复利改进机制

每个功能、重要缺陷或事故完成后，必须回答：

1. 哪个环节造成最多延迟、返工或失败？
2. 根因是什么？现有测试或门禁为什么没有拦住？
3. 最小的持久防护是什么？
4. 谁负责、以什么可观察条件完成？
5. 该经验应进入测试、CI、运行时保护、脚本、模板、模块文档还是全局规范？

可重复缺陷第二次发生时，除修复业务代码外，必须新增回归测试或其他可验证控制；若无法自动化，记录原因、补偿控制和复查时间。不能只往 `AGENTS.md` 增加一句模糊提醒。

长期跟踪：同类缺陷复发、发现到增加防护的时间、需求不清造成的返工、CI 反馈/恢复时间、用户任务完成率、有效澄清率、人工转接成功率和虚假成功事件。

## 10. 多 worker 并发认领协议

同一仓库可能有多个每小时自动化同时工作。工作日志里记录过：并发 worker 会
`git commit -a`、切换分支、把别人的 PR squash 合入 main、整体还原文档文件。
「大家注意别重复」不是控制措施（第 8 节），所以认领必须落成脚本与闸门。

### 10.1 不变量

> 一个 Issue 的**有效 claim 中 comment id 最小者唯一**，因此最多一个 worker 获准。

GitHub 的 `POST /issues/{n}/assignees` 是追加语义而不是排他锁，两个 worker 同时
认领会都挂上；label 同理。判定权因此放在 **claim comment 的服务端单调 id** 上：
id 由 GitHub 分配、唯一、单调递增，与并发时序无关。`flock` 只负责本机
「挑选 Issue → 发 claim」这一段不撞车，跨主机时即使失效也不会造成两人同时开工。

### 10.2 四层控制

| 层 | 控制 | 失败行为 |
|---|---|---|
| L1 认领 | `scripts/issue_claim.py next`：`flock` + 发 claim comment + **回读全部** + 最小 id 判定 + 写后再回读确认 | 没领到立即退出本轮，不换题重试 |
| L2 隔离 | 每个 worker 用独立 `git worktree`，分支 `issue/<n>-<worker_id>`；只 `git add <具体路径>`，禁用 `commit -a` / `add -A` | 物理上无法互相覆盖文件 |
| L3 合并前复核 | `guard <n>`：Issue 仍 open、自己仍是 winner、无竞争分支、main 未含 `Closes #n`、两项 CI 全 success | 任一不满足即丢弃分支，不合并 |
| L4 幂等兜底 | PR 正文写 `Closes #n`，squash 合并自动关 Issue；空 diff / 冲突的后来者 PR 直接关闭 | 不 rebase 覆盖别人的成果 |

L3 是唯一不依赖「所有 worker 都守协议」的一道闸门，不能省。

### 10.3 脚本契约

```bash
export WORKPANDA_WORKER_ID=worker1          # 每个 worker 唯一，必填
python scripts/issue_claim.py list          # 只读：列出可自动认领的 Issue
python scripts/issue_claim.py next          # 主入口：领下一个，输出 JSON
python scripts/issue_claim.py claim 27      # 领指定 Issue
python scripts/issue_claim.py release 27    # 释放自己当前获准的那条 claim
python scripts/issue_claim.py guard 27 --sha <sha>   # 合并前复核
```

退出码：`0` 获准 / 通过，`2` 未获准，`3` guard 拒绝，`4` 配置或 API 错误。
凭据优先取 `GITHUB_TOKEN`，否则走 `git credential fill`，不入库。
锁文件默认 `~/.workbuddy/locks/workpanda-issue-claim.lock`，**必须放在仓库之外**。

两条容易写错的地方：

1. **释放必须指向具体的 claim comment id**。按 worker 名释放会跨轮误伤——
   上一轮的 release 会把同一 worker 下一轮的新 claim 一起作废；
2. **判输者必须立刻撤回自己的 claim**。否则会留下一条「从没开工却占着位置」
   的记录，winner 释放后 Issue 仍被锁住（这是真实 API 验证时暴露的缺陷，
   已由 `tests/test_issue_claim.py::test_loser_withdraws_so_issue_becomes_reclaimable` 覆盖）。

### 10.4 边界

- 只有 `enhancement` 且无 assignee、无 `issue/<n>-*` 远端分支、无有效 claim 的
  Issue 会被自动认领；`question`（需决策）与 `documentation`（总览/合规前置）
  不自动领取，对应第 3 节「高风险任务不能由 AI 自行领取」；
- claim 默认 TTL 7200 秒，过期视为失效，避免 worker 崩溃后永久占位；
  该 Issue 已有 open PR 时放宽 4 倍，但保留上界；TTL 必须长于一次修复的
  最坏耗时，否则会出现租约中途过期、两人同时在跑；
- 这套机制只对**走同一脚本**的 worker 成立；绕过协议时只能靠 L3 兜底。

### 10.5 验证证据

`tests/test_issue_claim.py` 用带锁的 fake GitHub（服务端自增 comment id）跑
20 轮双线程真并发，断言每轮**有且仅有一个** worker 获准；另覆盖过期、
TTL 放宽、精确释放、旧格式释放被忽略、输者撤回、guard 的 CI/竞争分支/
已合并拒绝。真实 GitHub API 上也做过一次双进程并发认领 + 撤回 + 释放 +
guard 复核的端到端验证。

### 10.6 跨环境部署清单

协议以 GitHub 为唯一真相源，因此任何能访问同一仓库的云主机都能直接复用，
无需共享文件系统或中控服务。在新环境启用前，逐项确认：

1. **令牌**：设置 `GITHUB_TOKEN`，或在主机配好 `git credential manager`。
   脚本优先读 `GITHUB_TOKEN`，否则走 `git credential fill`，绝不入库。
2. **运行依赖**：`git` + `Python 3`（纯标准库，无需 `pip install`）。
3. **仓库与脚本路径**：worker prompt 里的仓库路径、脚本绝对路径必须换成
   新主机的实际路径；脚本本身用 `Path.home()` 与 `WORKPANDA_CLAIM_LOCK`
   环境变量推导锁与 worktree 位置，是 portable 的。
4. **本机锁跨平台**：`claim_lock()` 在 Unix 用 `fcntl.flock`、Windows 用
   `msvcrt.locking`，两者皆缺时退化为「不锁 + 警告」而非崩溃。锁文件默认
   `~/.workbuddy/locks/workpanda-issue-claim.lock`，可用 `WORKPANDA_CLAIM_LOCK`
   覆盖；锁按主机各自持有，本就不跨主机共享。
5. **每 worker 唯一编号**：`WORKPANDA_WORKER_ID` 必须唯一，否则仲裁判定会出错。
6. **租约 TTL**：`WORKPANDA_CLAIM_TTL_SECONDS`（默认 7200）须长于单次修复的
   最坏耗时，否则租约中途过期会出现两人同时开工。

跨主机的正确性不依赖本机锁，而依赖服务端 comment id 仲裁；本机锁只是减少
无效认领的优化，缺失时最多多一条被撤回的 claim。
