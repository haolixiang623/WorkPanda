# WorkPanda 开发运营机制

> 本文件把 `AGENTS.md` 和 `design/DESIGN.md` 中的工程约束落成可持续运行的开发机制。目标不是让 AI 无限制地自动写代码，而是让 AI 在已批准的边界内持续交付可验证的小切片，并把每轮反馈沉淀为下一轮的效率和质量提升。

## 1. 核心运行模型

```text
产品目标 → 可执行需求 → 风险分级 → 方案/设计评审
  → AI 隔离实现 → 自动验证 → 人工审查 → 测试环境
  → 小范围试点 → 运行/用户反馈 → 复盘与防回归 → 下一轮需求
```

人类负责业务目标、政策规则、风险承担和发布批准；AI 负责已批准任务的探索、实现、测试、文档和证据整理；CI 和运行系统负责自动验证、反馈和可追溯性。

## 2. 人机职责

### AI 可自动执行

- 阅读仓库规范、需求和相关代码；
- 分析任务并提出实现计划；
- 在隔离分支中实现低风险小切片；
- 增加测试、运行仓库已有检查、修复当前分支的 CI 问题；
- 生成草稿 PR、验证报告和复盘候选项；
- 将已确认的重复问题转成回归测试、脚本或改进任务。

### 必须由人确认

- 业务政策、首期事项、身份/实名策略和人工渠道；
- 流程步骤、工具白名单、权限模型和关键动作确认语义；
- 敏感数据、数据库迁移、认证方式和外部副作用；
- 生产发布、凭据变更、停用和事故处置；
- 高风险设计、业务规则和无法验证的结果。

AI 生成的代码不降低任何测试、审查、隐私或发布标准。

## 3. 任务生命周期

任务状态统一使用以下语义：

```text
候选 → 待确认 → 已批准 → AI 实现中 → 待验证 → 待人工审核
→ 待测试环境 → 试点中 → 已完成
```

异常状态必须区分：`需求不清`、`技术阻塞`、`测试失败`、`业务审核失败`、`安全审查失败`、`用户验证失败`。

### 任务进入 AI 队列的条件

低风险任务只有同时满足以下条件，才可标记为 `ai-eligible`：

- 用户问题、预期结果和非目标明确；
- 验收标准可观察、可验证；
- 修改范围和依赖明确；
- 风险等级已标注；
- 不涉及未批准的政策、权限、敏感数据或生产操作。

中风险任务需人工确认计划；高风险任务需先完成设计和责任人批准，不能由 AI 自行领取。

## 4. 标准 AI Coding 流程

1. **探索**：读取 `AGENTS.md`、相关设计/需求/架构、现有代码和测试；检查仓库实际可用的命令。
2. **计划**：列出目标、非目标、影响文件、风险、状态变化和验证计划。需求不清时先停下提问。
3. **实现**：一次只做一个完整垂直切片，不顺手重构无关代码；所有工作在隔离分支或 worktree 中完成。
4. **验证**：先跑最相关检查，再跑项目已有的完整检查；补充正常路径、失败路径和“不应发生”的负向测试。
5. **交付**：创建草稿 PR，记录变更、命令、结果、未验证事项、数据/权限影响和剩余风险。
6. **审核**：AI 审查只能补充，不能替代人工批准；高风险变更由对应业务/技术责任人审核。
7. **复盘**：把重复问题转为测试、CI、运行时保护、脚本、模板或明确的改进任务。

仓库没有技术栈或测试命令时，必须如实报告“尚未具备该项验证”，不得臆造命令或声称通过。

## 5. 风险与权限门禁

| 等级 | 示例 | AI 默认权限 | 必需门禁 |
|---|---|---|---|
| 低 | 展示、公开信息、非关键文案 | 可隔离实现并提草稿 PR | 自动检查 + 人工审查 |
| 中 | 表单、任务状态、会话、浏览器自动化 | 需批准计划 | 授权/隔离/失败/隐私测试 |
| 高 | 提交、发送、改业务数据、认证、权限、敏感数据 | 不自动领取 | 设计审查 + 业务/技术批准 + 负向测试 |

任何变更跨越多个等级，按较高等级处理。禁止 AI 访问生产凭据、生产数据或未经批准的外部服务。

## 6. WorkPanda 专用质量门禁

涉及业务流程或副作用的变更，至少验证：

- 缺参或歧义不会启动副作用；
- 工具只能调用当前流程节点白名单；
- 关键动作由服务端校验用户、任务、流程版本、参数摘要和一次性确认凭证；
- 重复请求不会造成不可幂等副作用；
- 外部结果未知时显示“状态待确认”，不得盲目重试；
- 超时、取消、断线、恢复和转人工不会产生虚假成功；
- 用户会话、浏览器 profile、日志和测试夹具相互隔离且不泄露敏感值。

涉及群众侧 UI 的变更，还必须遵循 `design/DESIGN.md` 的状态、无障碍、响应式和内容约束。

## 7. 分支、PR 与发布

- 主分支只接受通过 CI 和人工审核的 PR；
- 一个 PR 尽量对应一个可审查的行为变化；
- CI 失败优先修复，不能在不稳定基线上继续堆叠功能；
- PR 必须附准确的验证命令和结果，未运行的检查明确列出；
- 高风险功能先在测试环境或受限范围试点；
- 发布前确认人工转接、停用开关、监控和回滚路径可用；
- 发生越权、个人数据暴露、重复副作用或虚假成功时，立即停用受影响流程并启动事故处理。

在技术栈和部署链路确定前，不自动启用生产发布。

## 8. 复利改进机制

每个功能、重要缺陷或事故完成后，必须回答：

1. 哪个环节造成最多延迟、返工或失败？
2. 根因是什么？现有测试或门禁为什么没有拦住？
3. 最小的持久防护是什么？
4. 谁负责、以什么可观察条件完成？
5. 该经验应进入测试、CI、运行时保护、脚本、模板、模块文档还是全局规范？

可重复缺陷第二次发生时，除修复业务代码外，必须新增回归测试或其他可验证控制；若无法自动化，记录原因、补偿控制和复查时间。不能只往 `AGENTS.md` 增加一句模糊提醒。

长期跟踪：同类缺陷复发、发现到增加防护的时间、需求不清造成的返工、CI 反馈/恢复时间、用户任务完成率、有效澄清率、人工转接成功率和虚假成功事件。

## 9. 当前落地顺序

已完成：

- 工程骨架：FastAPI 宿主、固定流程、状态机、确认凭证、事件流、内存与 SQLite 存储、基础测试与 CI 入口。

进行中与后续：

1. 确认首期低风险试点事项、身份策略、人工渠道和数据留存要求；
2. 把 SQLite 替换为 PostgreSQL，并加入迁移和备份策略；
3. 使用本仓库的 Issue/PR 模板进入第一个业务任务；
4. 接入真实意图分类与槽位抽取，并建立版本化评测集；
5. 交付第一个端到端低风险业务切片，覆盖输入、识别、澄清、状态、结果、失败和转人工；
6. 建立意图/澄清评测集、流程负向测试和 UI 状态回归集；
7. 运行小范围试点后，再开放真实执行器、确认凭证和更高风险流程。

首期不把多 Agent、长期记忆、复杂向量检索、全面浏览器自动化和自动生产发布设为前置条件。
