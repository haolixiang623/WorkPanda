## 1. 架构决策（8 条，请逐条批注）

### D0. 目标场景：任意「固定流程服务」，不限于政务

**决策**：产品定位上提一档。凡是同时满足四个条件的场景都算目标场景——流程由运营方
定义并维护、用户只通过对话表达、执行会产生外部副作用、结果必须可核验（成功/失败/
待确认三态）。政务办事只是其中一类，企业客服受理、内部审批、运营商/银行网点业务
办理、平台申诉与理赔，都属于同一形态。

**理由**：本项目真正的技术内核不是「政务」，而是**受监管流程的正确性**——版本不可变、
发布指针、副作用不可重复、结果未知不得当失败、每步授权可审计。这些约束在政务场景
最刚性，但在任何有副作用的流程服务里都成立。把定位钉在政务上，会让后续设计不必要地
依赖政务特有的东西（实名库、政务服务网、事项编码），从而在别的场景里返工。

**对设计的四条约束**
1. **不得依赖政务专有基础设施**：身份、材料、回执都按「可替换的外部系统」对待；
2. **IM 渠道不能按政务选型**：第一个渠道选企业微信是因为企业侧覆盖率，不是因为它"政务"；
3. **「服务对象」不预设实名强度**：有的场景是匿名群众，有的是已登录客户，身份强度
   由场景配置决定，不能写死在代码里；
4. **数据留存期限必须可配置**：不同行业要求不同，不能定死一个数字。

**措辞约定**：代码与既有文档里的「群众」暂不批量替换（改动面大、收益低，且容易与
`citizen` 类型名冲突）；**新增文档与对外文案统一用「服务对象 / 用户」**，需要指代
匿名入口时明确写「匿名会话用户」。

---

### D1. 新增「工作人员（staff）」作为第四类主体，不并入 admin

**决策**：主体分四类——群众（匿名会话）、运维（ops token）、管理（admin token）、
工作人员（staff）。staff 办业务（受理、复核、审批），权限按「能对哪些流程做什么动作」
授予，而不是继承 admin。

**理由**：现在系统里只有三类，且 `docs/ARCHITECTURE.md:153` 明说群众令牌「不是实名身份，
不能作为办事资格或政策判断依据」。把工作人员塞进 admin，等于让每个办事员都能改
「哪一步需要群众确认」——那正是 `docs/ADMIN-CONSOLE.md` 第 6 节标为「高风险，启用前须
业务/安全责任人确认」的能力。两类人的权限量级差一个数量级，不能共用一个角色。

**代价**：多一套凭据、多一套角色判定、多一组回归。这是本轮最贵的一条。

### D2. IM 网关是通道，不是执行者，也不是权限来源

**决策**：网关放在 `infrastructure` 层，只做四件事——验签、归一化、查身份映射、调
**同一套** application service。不允许自行拼 `TaskService`，更不允许直连 harness。

**理由**：项目已经付过一次代价——删掉 Octop 作为 Executor，因为整步委托让「某次副作用
是否发生」无法证明（`docs/HARNESS.md` 第 2 节）。消息传输层不产生副作用，所以接入 IM 网关
不与那次决策矛盾；但它一旦能自己驱动流程，就会重开那个口子。

**代价**：网关永远比 IM 平台晚一档能力，复杂交互要先落成 API 再做卡片。

### D3. 确认凭证不得由 IM 消息签发（红线）

**决策**：IM 卡片只放**一次性深链**，点开回到 Web 完成确认凭证签发。IM 里回「确认」
两个字不构成任何授权。

**理由**：现有确认凭证绑定 `task + flow_version + step + 参数摘要 + user_ref + TTL`。
IM 文本绑定不了参数摘要，也挡不住转发、代回、群里「我也同意」、截图伪造。为了少点
一次跳转牺牲这条，等于把三态结果契约里「群众确认」这一段整体掏空，而且失守时无声无息。

**代价**：多一次跳转，移动端体验变差。这条我建议不妥协。

### D4. IM 身份映射是显式数据，不靠「来自 IM 即员工」推断

**决策**：`im_user_id → principal(subject, roles)` 存库，由管理侧维护。未映射的 IM 用户
按「匿名会话 + 一个 IM 侧标识」处理，不得当实名。

**理由**：企业微信可以同时挂外部联系人（群众走微信、工作人员走企微），这是天然的双通道，
但**外部联系人的身份完全不受控**。用「消息来自 IM 网关」推断员工身份，等于把外部联系人
一起提权。

**代价**：新员工入职要在两个系统各配一次；需要一条同步或导入脚本。

### D5. 补上发布署名：`publish(actor)` + `published_by`

**决策**：`FlowStore.publish` 增加 `actor` 参数，`flow_releases` 增加 `published_by`、
`disabled_by`、`updated_by`；`/api/admin/flows/*` 从**凭据主体**取 actor，不接受请求体自报。

**现状（这是缺口，不是偏好）**：

```python
# src/workpanda/domain/flow.py:100
def publish(self, flow_id: str, version: str) -> None: ...
# flow_releases: (flow_id, published_version, updated_at) —— 没有「谁」
```

对比同一项目里对「人工备注」的处理（`src/workpanda/api/ops.py`）：署名取自已鉴权的
运维主体，**不读请求体**，理由是「可自报的署名等于没有署名」。

**结论**：一条备注要署名，而「把一条流程推上线」不署名。现在谁也说不清是哪个人把某条
流程推上线的。这是「谁有权把流程推上线」这个责任能不能落到人身上的前提。

**代价**：一次 schema 迁移 + 全链路签名改动（接口、CLI、测试）。小，但会碰到几个调用点。

**已定：不做双人复核（四眼原则）。** 用户 2026-11-08 明确决定。因此 `flow_releases`
**只有 `published_by`，不预留 `reviewed_by`**——留一个永远为空的字段比不留更糟，它会让
后来的人以为"复核环节存在但没人用"，而不是"没有这个环节"。若将来确有场景需要，
那是新增一张复核表 + 状态机的事，不是给这张表加一列。

不做复核的连带结论：**发布是单人动作，所以署名的可信度就是这条链路唯一的责任锚点**。
这也是 D5 必须做的原因——没有复核兜底，又没有署名，等于发布无人负责。

### D6. 管理侧表单必须能录意图样例，否则配置台「只能建不能发」

**决策**：把 `intent_samples` 录入纳入管理侧表单，作为发布前置条件。

**现状**：`docs/ADMIN-CONSOLE.md` 第 6 节第 4 条自己写着——

> 本轮表单没有样例录入项，所以**只用界面建出来的流程没有样例，发布会返回 409**
> （`admin_intent_gate_blocked`）

也就是说 #58 与 #59 合起来的净效果是：**运维在界面上建一条新流程，一定发不出去。**
门禁本身是对的（我认同 #59 的设计），但唯一入口建不出可发布流程，配置台对运维就不成立。

**代价**：表单加一个动态列表控件 + 校验（≥N 正例、≥M 近似误例）+ 一条端到端回归。

### D7. 桌面客户端不自建，先「IM 卡片 + Web 深链」；若自建则是纯壳

**决策**：工作人员侧第一版 = IM 卡片 + 浏览器深链，桌面端就是 IM 本身。若之后确实要
自建客户端，它是一个**只做展示与导航的壳**：不存业务数据、不做本地业务判断、不缓存确认凭证。

**理由**：自建桌面端的成本不在 UI，在三样很贵的东西——自动更新链、本地凭据存储
（比浏览器 cookie 危险一档）、离线状态一致性。这些成本必须换来对等收益，而现阶段收益
主要是「少开一个浏览器」，不成立。

**代价**：工作人员仍要在 IM 和浏览器之间切换。

### D8. 多实例发布一致性是「启用多实例的前置条件」，不是优化项

**决策**：在多实例上线前，必须先定义发布广播；或明确限制「管理侧只在单实例上开放」。

**现状**：`docs/ADMIN-CONSOLE.md` 第 6 节第 2 条：`reload()` 只更新当前进程；多实例时
其它实例仍持旧目录。这是已经写进文档的已知限制，我同意它的判断——只是它现在挂在
「影响面与已知限制」里，容易被当成注意事项而不是门禁。

**理由**：发布不一致的后果是「一部分群众走新流程、一部分走旧流程」，比发布失败更糟，
因为它不报错。

**代价**：#60 已给出容量阈值，但阈值触发时如果没有广播机制，扩容就要先补这块。

### N2 · 发布署名

**用户问题**：流程被推上线后，事后无法回答「谁在什么时候把 v3 换成了 v4」。

**范围**
1. `FlowStore.publish(flow_id, version, *, actor: str)`、`disable(flow_id, *, actor)`；
2. `flow_releases` 增 `published_by`、`disabled_by`，含迁移（回滚走 `publish`，因此
   `published_by` 一并覆盖「谁回滚的」）；
3. `/api/admin/flows/*` 从凭据主体取 actor，**不接受请求体自报**；
4. `admin-ui` 的发布/回滚/停用结果展示署名。

**非目标**：不做多级审批，**不做双人复核、不预留 `reviewed_by`**（第 4 节问题 5 已决）。

**验收**
- `actor` 是仅关键字必填参数，漏传是类型错误，不会静默默认成空串；
- 接口返回体里的署名等于凭据主体名，伪造请求体字段无效（有回归）；
- 迁移后旧数据 `published_by` 为 `NULL` 且读取不报错；
- `pytest` 全绿，`ruff` 全过。

### N3 · 表单补意图样例录入

**用户问题**：运维在界面上建一条新流程，发布会必然 409。

**范围**
1. 表单增意图样例动态列表（正例 / 近似误例 / 超范围例），带条数校验；
2. 提交前本地预校验，把缺哪类、缺几条直接显示，不等服务端 409；
3. 端到端回归：界面建草稿（含样例）→ 回放 → 发布成功。

**非目标**：不做样例自动生成；不做规则路由的自动装配（仍在装配期代码）。

**验收**
- 只用界面建出的流程能发布成功（回归钉住）；
- 样例不足时按钮禁用并写明缺什么，而不是发出去再吃 409。

### N1 · 主体模型 + IM 身份映射

**用户问题**：系统里「工作人员」这个主体不存在，IM 接入没有落点。

**范围**
1. `Principal(subject, kind: citizen|staff|ops|admin, roles)`，四类通道凭据互不认账
   （沿用 `docs/OPS-ACCESS-CONTROL.md` 第 3 节与三套凭据的既有做法）；
2. `im_identities` 映射表（`channel`, `im_user_id`, `principal_subject`, `enabled`）；
3. 管理侧维护映射的接口（沿用 admin 凭据）；
4. 未映射用户的行为明确定义：拒绝并留痕，不降级为群众会话。

**非目标**：不做组织架构同步（先手工维护，跑通再谈同步）。

**验收**
- 四类凭据交叉使用全部 401（每类一条回归）；
- 未映射的 IM 用户被拒绝，且拒绝记录里有 IM 标识（可追溯）；
- 映射表变更后无需重启即生效。

### N4 · 企业微信网关 adapter

**用户问题**：工作人员在企微里，不想为了看一眼任务再开浏览器。

**范围**
1. 入站 webhook：验签 → 幂等去重（IM 会重投，按 message id）→ 归一化；
2. 身份解析走 N1 的映射表；
3. 出站：任务事件 → 卡片（只含状态与一个深链，不含群众数据正文）；
4. 送达失败只记日志不阻塞流程（fail-open on notification）。

**非目标**：不在 IM 里做业务操作；不做群机器人广播；不接第二个渠道。

**验收**
- 重投同一 message id 只处理一次（有回归）；
- 验签失败一律拒绝，不进入业务层；
- 通知失败不影响任务推进（有回归）。

### N5 · 卡片深链确认

**用户问题**：工作人员要在 IM 里把任务推进到下一步，但不能降低授权强度。

**范围**
1. 卡片按钮 → 一次性深链（短 TTL、绑定 task + step）→ 浏览器带既有会话完成确认；
2. **回归红线**：IM 文本回复（包括「确认」「yes」「同意」）不得签发任何确认凭证；
3. 深链被重放/过期/跨任务使用时全部拒绝并留痕。

**非目标**：不做 IM 内免跳转确认（D3）。

**验收**
- 上述红线的回归用例必须在 CI 里；
- 深链一次性、TTL 到期、跨任务三个负例各一条。

### N6 · 多实例发布同步

**范围**：发布后广播到所有实例（或在管理面明确限制单实例）；给出「发布后 N 秒内全实例一致」
的可观测判据。

**验收**：多实例下发布后所有实例在约定时限内一致，且可监测。

### N7 · 桌面壳（可选，本轮不做）

**范围**：纯展示 + 导航的壳，内嵌 web；不存业务数据、不缓存凭证。
