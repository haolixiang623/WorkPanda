# 决策：控制台是否开放写工具

> 对应 Issue #30。结论：**go，但只开一条"追加事实"的窄通道；"重试"与"改状态"永久 no-go。**
> 实现见 `POST /api/ops/tasks/{task_id}/notes`，只读边界仍受 `docs/OCTOP-INTEGRATION.md` 4.2 约束。

## 1. 问题

控制台（Octop）此前严格只读。运营遇到三类情况时，系统里无处置落点，只能记在系统外：

1. 群众来电撤销，但已关掉页面、会话失效，任务停在执行中——运营无法替他取消，任务永久悬挂；
2. 提交超时，任务落到 `outcome_unconfirmed`，运营去对方系统查到其实已办成——系统里仍是"待确认"，谁也推不动，换个人接手还要再查一遍；
3. 群众说来办过、单据也在手上，运营核对属实——系统里没有任何地方能留下"已核实"。

三件事的共同点：**外部事实已经推进，Task Store 不知道。** 系统里的记录与现实脱节，事后无法复盘当时核实到了什么。

## 2. 决策

| 档位 | 能力 | 结论 | 理由 |
|---|---|---|---|
| A | 追加人工处置备注（不改状态） | **go，本次实现** | 只补充事实，不改变任何结论，风险最低而价值最高 |
| B | 运营代人取消任务 | **不做**（需另开设计） | 群众侧已有 `cancel`；运营侧需要具名身份才谈得上追责，前置未满足 |
| C | 重试 / 重放步骤 | **永久 no-go** | 可能让已提交的副作用再发生一次：群众被扣两次钱、收到两份材料 |
| D | 直接覆写任务状态 | **永久 no-go** | 把虚假成功制度化，正是结构化结果契约要消灭的缺陷 |

**分界线是「追加 vs 覆写」，不是「读 vs 写」。** A 档之所以安全，是因为它没有 `status` 字段可填——少一个字段就少一条覆写路径。

## 3. A 档的实现约束

| 约束 | 做法 |
|---|---|
| 不改任务状态 | 请求体没有 `status` 字段；多余字段被忽略（有测试锁定） |
| 不写整行 | 只调 `TaskStore.append_event`，不走 `commit`。走 `commit` 会把入口读到的旧快照整体写回，覆盖期间 `answer` 刚写入的 `slots` |
| 任何状态都允许 | 含终态。**终态才是主场**：`handoff_required` / `cancelled` 之后的事实最需要留痕 |
| 群众不可见 | `operator_note` 属于 `_OPERATOR_ONLY_EVENTS`，群众侧 SSE 与事件接口一律过滤。备注里多是"疑似重复申请""待回单"这类内部判断，推给群众等于泄露核查线索 |
| 长度受限 | `operator` ≤64、`note` ≤1000、`reference` ≤200。备注长期留在事件流里，不设上限等于变相塞文件 |
| 不做条件写 | 条件写的语义是"我的决策基于读到的状态"。备注不做决策、不改状态，因此不适用；它不碰状态那一路，也就谈不上放宽门禁 |

## 4. 永久禁止项（钉死）

以下三条不得以"运维方便"为由实现，需要时先重开设计评审：

1. **重放 `outcome_unconfirmed` / `failed` 的步骤。** 状态机当前只有 `OUTCOME_UNCONFIRMED → HANDOFF_REQUIRED` 一条出口，注释写明"结果未知时不能自动重试"。开重试等于先推翻这条安全规则。
2. **把任意状态改成 `completed` / `failed`。** 群众会收到一次没有自己动作的状态跳变，而确认凭证（绑定任务、步骤、参数摘要）可能仍然有效。
3. **绕过群众确认签发凭证。** 确认语义只能由群众侧完成。

## 5. 已知未解决（不阻塞 A 档，阻塞 B 档）

1. **`operator` 是自述字段，不是鉴权身份。** 运维凭据当前是单一共享 token（`WORKPANDA_OPS_TOKEN`），服务端无法证明是谁在操作。因此备注只能用于留痕，**不能作为处罚或追责依据**。换成每操作者独立凭据之前，不要把"A 做过"当成事实。这一条已写进 `TaskNoteRequest` 的文档字符串。
2. **跨执行幂等账本仍缺。** 防重复副作用的 `_succeeded_effects` 是执行器实例内存，只覆盖单次执行；`effects.py` 的 `fingerprint` 已落审计，但还没有读回来做跨执行比对的逻辑。这是 B 档（代人取消）之外任何"重放类"能力的前置。
3. **备注的保留期与脱敏口径未定。** 备注可能被写入群众信息。当前只做长度限制，未过 `redaction`。涉及数据留存期限，属于政策决策，不在此单方面决定。

## 6. 验证证据

`tests/test_ops_operator_note.py`（10 例）：

- 备注进入运维事件流，字段完整；
- **不改** `status`、`updated_at`、`slots`、`current_step`；
- 终态（`cancelled`）可加备注，且加完仍是终态；
- 群众侧 SSE 不含 `operator_note`，也不含备注正文，同时正常事件不被误伤；
- 缺 `operator`、空 `operator`、超长 `note` 均 422；
- 请求体夹带 `status: completed` 被忽略，状态不变；
- 缺凭据 401、`/api/ops` 未启用 404、任务不存在 404。

回归：`ruff check .` 通过，`pytest` 全量通过（见 PR）。

## 7. 回滚

纯新增：一个事件类型、一个端点、一处群众侧过滤。回滚即删除这三处，不涉及数据迁移——已写入的 `operator_note` 事件留在库里，读不到也不会影响状态机（状态机不认这个事件类型）。
