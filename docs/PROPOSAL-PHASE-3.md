## 0. 一句话结论

D1 选的是「本地模拟三方站」，这把这个项目的性质校准了：**首期不是"接一个真实政务站"，
而是"用可控的三方站把浏览器执行链路整条打通"**。这是对的选择——真实站点会把政策、
合规、实名、留存这些事情一次性压到脸上，而它们现在都还没定。模拟站让 G6（API 优先、
浏览器补位、群众操作兜底）第一次真正可测。

代价是链路比原计划长，且暴露出我上一版漏看的一处：**群众侧 Web/H5 界面根本不存在**
（见第 1 节更正）。

## 4. 阶段 3 的四个 issue（草稿）

### T1 · 认领协议：PR 延长 TTL 不得复活没有产出的旧认领（D3 = A）

**用户问题**：#68（worker3）、#69（worker1）两份完整实现，门禁全绿、远端 CI 全过，
仍被判 `lost_arbitration` 丢弃；#61 至今 open。同一个任务做了两遍、两次归零。

**根因**：`scripts/issue_claim.py:168`

```python
multiplier = PR_TTL_MULTIPLIER if has_open_pr else 1     # has_open_pr 是全局布尔
if now - claim.created_at > timedelta(seconds=claim.ttl_seconds * multiplier):
    continue
```

`_has_open_pr(pulls, number)` 只看分支前缀 `issue/<n>-`，不看是谁开的。当前 worker 一开 PR，
该 Issue 上**所有**历史 claim 一起 ×4：06:18:06Z 创建、从未产出分支或 PR、08:18:06Z 已过期的
`interactive` 认领被复活到 14:18:06Z，其 comment_id 更小 → 判赢的是它。

**范围**（按 D3=A）
1. `_has_open_pr` 改为返回**worker 集合**（分支前缀 + PR head 分支里的 worker 标识）；
2. `arbitrate()` / `active_claims()` 的倍率只作用于 `claim.worker_id ∈ 该集合` 的 claim；
3. 主判定保持"最小 comment id 获胜"不变，只修倍率作用范围。

**非目标**：不改认领的凭据与锁机制；不引入续期子命令（D3 的 B 案）。

**验收**
- 参数化回归：过期且无产出的 claim + 新鲜 claim + 刚开的 PR → 新鲜者获准（这是 #68/#69 的现场）；
- `list` / `next` / `guard` 三条路径对同一条过期 claim 的判定必须一致；
- 现有 `issue_claim.py` 的仲裁逻辑**零自动化覆盖**，本 issue 必须补上，否则它会第三次坏掉。

**规模**：小（1 文件 + 1 测试文件）· **依赖**：无

### T2 · 意图规则进流程定义 + 发布后重建路由器（D2 = B）

**用户问题（两个现象，一个根因）**
- 现象一：管理侧发布 v2 后，群众用自然语言仍被送到 v1；v1 已不是发布版本 → 群众看到 422。
- 现象二：运维在配置台建好流程并发布成功，**群众怎么说都命中不了**——规则集来自代码常量。

**本地复现**（`/tmp` 脚本，未改仓库）

```
规则： [('demo.generic', '1')]
识别结果： matched ('demo.generic', '1')
群众侧报错： FlowNotRunnable flow 'demo.generic' is not published
按 flow_id 不带版本 resolve： 9.9.9
```

**根因三处叠加**
1. `bootstrap.build_intent_router()` 只在启动跑一次；`admin_flows.py` 四处 `registry.reload()`，
   **零处重建路由器**；
2. `default_intent_rules()` 只是按 `(flow_id, version)` 过滤 `demo_intent_rules()` 这个代码常量；
3. `task_service._resolve_flow()` 用 `resolve(flow_id, match.flow_version)` 带版本解析，
   规则里写死的旧版本号会精确落到旧版本，指针一动必然失败。

**范围**（按 D2=B：规则显式进流程定义）
1. `FlowDefinition` 增显式规则字段（关键词 + 槽位模式），随版本不可变、随发布生效；
   校验：规则必须指向自身 `flow_id`，引用未声明字段的槽位模式直接拒绝（`flow_field_errors` 加一条）；
2. 发布 / 回滚 / 停用之后**原地重建**规则表，沿用 `FlowRegistry.reload()` 同款做法——
   保持路由器对象身份不变，否则 `TaskService` 拿着旧引用等于没修；
3. 版本解耦：命中后走 `resolve(flow_id)` 取当前指针，不用规则里的旧版本号；
   在途任务仍用 `require(flow_id, 版本)`；
4. 装配期不再依赖 `demo_intent_rules()` 代码常量（自检流程自己声明规则即可）。

**非目标**：不自动从样例派生关键词（D2 已否决 A 案）；不做规则的可视化调试器。

**验收**
- 端到端：界面建流程（含规则与样例）→ 发布 → 群众自然语言建任务成功，
  且 `task.flow_version` = 发布指针版本；
- 发布 v2 后同一句话落到 v2，不再出现 `FlowNotRunnable`；回滚后落到 v1；
- 停用后同一句话走澄清（`IntentUnresolved`），**不得**落到已停用流程；
- 规则引用未声明字段时，保存草稿即被字段级校验拒绝；
- 必须有一条**从自然语言入口发起**的回归。现有 `test_publish_makes_flow_hittable_by_citizen_side`
  走的是显式 `flow_id`（`tests/test_admin_flows_api.py:94` 注释写明），正好绕开路由器，
  所以一直没被抓到。

**规模**：中 · **依赖**：无（但与 T3 同区域，串行）

### P0 · 群众侧最小对话页（Web/H5）

**为什么必须现在做**：P3 的"需要用户操作 + 我已完成"、G4 的确认摘要、G5 的失败与转人工，
都需要一个页面。没有它，试点只能靠 curl 演示。

**形态**：`web/`（与 `admin-ui/` 同款：独立 TS/ESM + `tsc` 构建，产物提交），
服务端新增静态托管（默认只挂回环）。

**必须能表达的状态**（对齐 `design/DESIGN.md` §3.1，不新增语义）：空闲 / 已接收 /
正在识别 / 需要澄清 / 等待用户输入 / 等待确认 / 执行中 / **需要用户操作** / 已完成 /
失败 / 状态待确认 / 转人工 / 已取消。

**要点**
- 状态**只从服务端权威状态派生**，不允许按动画结束或请求超时推断完成；
- 澄清一次问一个关键字段；确认页展示动作、关键字段、影响；
- 需要用户操作时给出"去哪、做什么、多久过期" + **我已完成**按钮（该按钮只调
  `/api/tasks/{id}/answers`，**不是确认凭证**）；
- 断线重连按 task_id 从服务端恢复；
- 不把敏感字段写进 URL、DOM 属性或调试文案。

**验收**：一条端到端手工走查（含刷新重连、取消、转人工）；不把凭据写进构建产物（沿用管理侧
已有的敏感串扫描）。

**规模**：中 · **依赖**：无（可与 P1 并行）

### P2 · 浏览器执行器：契约 + 只读路径

**范围**
1. 引入 Playwright（服务端 headless），新增工具：`browser_open` / `browser_click` /
   `browser_read` / `browser_select` / `browser_check` / `browser_fill` / `browser_wait`；
2. **本 issue 只开到"进入填写页"，不允许点击提交**（提交留到 P4，且必须过确认凭证）；
3. 硬约束（架构 §4）：目标域名白名单（**含跳转后的第二站点，必须显式列出**）；

   下载目录限定；截图/DOM 落盘前脱敏；超时按"结果未知"，不当失败重试；
4. 定位失败、元素消失、页面改版 → 明确失败码 + 转人工，**不得**误报成功。

**依赖治理**（AGENTS.md「依赖项与自动化安全」）：Playwright 必须固定到不可变版本；
浏览器二进制不进仓库；CI 单开一个 job 装浏览器跑浏览器用例，**不允许把跳过当通过**
（跳过必须在报告里写明原因）。

**验收**
- 两个用户的 context 不共享 cookie（有回归）；
- 白名单外域名一律拒绝（含跳转后的站点，未列即拒）；
- 工具超时 → `OUTCOME_UNCONFIRMED`，不自动重试非幂等动作；
- 对 P1 的 `/login → /services → /apply` 走通只读路径；DOM 改版负例有回归。

**规模**：大 · **依赖**：P1（靶子）

**现状缺口**：`EventType` 无 `user_action_required`；`TaskStatus.WAITING_FOR_USER` 语义泛化。

**范围**
1. 新增 `EventType.USER_ACTION_REQUIRED`（架构 §7 已列，补齐实现）；`WAITING_FOR_USER`
   细分出"等用户自己操作"与"等用户补充字段"两种语义（可不加新状态，但事件必须能区分）；
2. 三种介入：图形验证码、扫码登录、附件上传（见 R1）——统一为"暂停 + 指引 + 我已完成 + 复检"；
3. **红线**：密码/验证码**永不**进入 slots、trace、日志、事件（有回归）；扫码只把二维码显示给用户，
   不代扫、不代持；"我已完成"只是切换信号，不签发确认凭证（与 D3 红线同源）；
4. 超时未完成 → 转人工，保留已完成步骤。

**验收**
- 密码/验证码字段在 trace、事件、日志里零命中（这是本 issue 的主回归）；
- 用户未完成时执行器不得继续（有回归）；
- 二维码过期的负例：给出"重新获取"，不报成功、不静默重试。

**规模**：中 · **依赖**：P2

### P4 · 试点流程 + 显式意图规则 + 样例集

**范围**
1. `demo.pilot` 流程：collect（电话/地址）→ **user_action**（登录）→ execute（选事项、跨站跳转、
   填 tab1）→ **user_action**（附件上传）→ execute（tab2/3 校验）→ confirm（摘要 + 群众确认凭证）

## 6. 待拍板三项（**已定，2026-11-09**）

三项都按本文档给出的默认值执行，原分析保留在下方，作为后续 issue 的决策依据。

| 项 | 决策 | 落点 |
|---|---|---|
| R1 | **附件不代传**：附件 tab 由用户在自己浏览器里上传，系统只做「去上传 → 我已完成 → 复检」 | P3、P4 |
| R2 | **群众侧最小对话页本轮做**（P0） | P0、P3、P4 |
| R3 | **一起改**：`active_claims()` 与 `arbitrate()` 共用同一份过期判定 | #71（已完成） |

### R1. 附件上传：服务端代传，还是引导用户自己传？

**我的默认：不代传。**（**已采纳**）附件 tab 由用户在自己浏览器里上传，我们只做"去上传 → 我已完成 → 复检"。
理由：一旦服务端代传，等于我们要承担材料留存期限、加密、删除、审计的整套义务，
而 `business-goals.md` 第 10 节的留存期限至今未定。用模拟站演示时，代传看不出差别，
但上线前一定会被这一条挡住。
**若你要代传**：请一并给留存期限与加密要求，否则这条不该开工。

### R2. 群众侧最小对话页，本轮做不做？

**我的默认：做（P0）。**（**已采纳**）不做的话，P3 的"我已完成"和 G4 的确认摘要没有承载物，
试点只能 curl 演示，等于 P1–P4 的成果无法给业务方看。
**若你想先只做后端**：那 P0 顺延，但 P4 的验收要改成"接口级端到端"。

### R3. D3 的倍率口径，是否连 `list`/`next` 一起改？

**我的默认：一起改。**（**已采纳，并于 #71 落地**）`active_claims()`（给 `list`/`next` 用）和 `arbitrate()`（给 `claim`/`guard`
用）当时是两份重复逻辑，同时犯同样的错。已抽成唯一的 `_is_active()`，claim / guard / list 三条路径共用，
并加了"三路径结论一致"的回归。
**若你只想先修 `arbitrate`**：可以，但要在 issue 里写明 `list`/`next` 暂留旧行为。
