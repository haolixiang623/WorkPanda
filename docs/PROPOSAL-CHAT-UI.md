# 群众端对话式交互落地：Issue 拆分草案

> 来源：`demo/citizen-interaction.html` 评审稿（对话式原型，未入库；含合成证件号样态，
> 需要时另行发布）。
> **状态：已审核（2026-11-09 19:00 UTC+8），B1–B3 已落地（2026-11-09 21:00 UTC+8），
> 尚未提交到 Issue 跟踪器。** 落地时按 B1 → B2 → B3 串行做完，三项各有一组回归；
> 与原设计的**差异**见文末「落地记录」，其中最关键的一条是 B1 **没有做**
> "`required_fields` 含敏感名却未声明就拒绝发布"的硬门禁——用户明确要求先跑通流程，
> 且"哪几个词算敏感"属业务口径，代码不该替运营定。保留的是"标错字段就拒绝保存"
> （它才是真正会静默失效的那条）。
> 落地目标：把原型里被评审确认的交互形态（对话框 + 常驻输入框）落成 `web/` 的真实实现，
> 不改变任何状态语义与写入通道。

## 0. 为什么不能"一个 PR 全做"

原型里有三处依赖**服务端目前不提供**的事实，页面自己补就等于替服务端编造：

| 页面想要 | 现在能拿到 | 缺什么 |
|---|---|---|
| 对话开场说"您要办的是：报修" | 只有 `current_step_title`（步骤名，不是事项名） | 流程标题 `FlowDefinition.title` 未下发 |
| 用户答复回显（身份证只显后四位） | `slots` 全是明文 | 字段的敏感标记，页面无从判断 |
| 办结屏显示"受理编号 R-1" | `result` 是执行器原始信封 | 结果白名单 + 中文字段名 |

此外 `Task` 不保存 `input_text`，群众第一句原话**在任何地方都取不回来**。

所以拆成 5 个切片，其中 1→2→3 串行（服务端给元数据 → 纯函数派生 → 渲染接入），
4、5 独立。

## 1. 依赖关系

```text
#1 服务端对话元数据 (flow_title + sensitive_fields)
        └── #2 transcript 纯函数
                    └── #3 页面改为对话式

#4 办结屏结果白名单（缺陷，独立）
#5 输入框附件入口（独立，需先决策上传能力）
```

## Issue 1：`[功能] 群众侧对话所需的两项元数据：流程标题与字段敏感标记`

- **标签**：`type:feature`
- **风险**：中 → 高（新增敏感数据分类口径，需业务确认）
- **阻塞**：#2、#3
- **影响范围**：涉及个人信息或敏感数据；涉及群众侧 UI

### 用户问题与预期结果

对话式界面有两句话必须由流程作者提供、页面不能自己编：

1. **开场要说"您要办的是哪件事"**。现在 `TaskView` 只有 `current_step_title`
   （"收集报修信息"），这是步骤名不是事项名。页面唯一的替代品是复述群众原话，而
   `Task` 根本没保存 `input_text`——它就是取不回来。
2. **答复要不要打码**。确认页和（未来的）对话记录都要回显已填内容。身份证号明文
   常驻屏幕是原型评审时已修过一次的问题（原型改为回显 `320501********1234`），但
   原型能这么写是因为内置事项自带 `mask` 标记；真实产品里页面没有任何依据判断
   哪个字段敏感，只能二选一：全部明文（放大暴露面）或全部不显示（用户看不懂在填什么）。

完成后：`TaskView` 带 `flow_title` 与 `sensitive_fields`，页面据此显示事项名并对敏感
字段打码，不需要按字段名猜。

### 范围与非目标

**做**：

- `FlowDefinition.title` 下发为 `TaskView.flow_title`（缺失时为 `None`，页面退回不显示）；
- `StepDefinition` 增加 `sensitive_fields: tuple[str, ...] = ()`，语义同既有
  `field_labels`：**覆盖这一版流程声明过的全部字段**；
- `TaskView.sensitive_fields: list[str]`（缺标签时为空列表，页面按"全部不敏感"处理
  会明文显示——这一点在验收里明确要求由**作者必须声明**来兜底，见下）；
- `demo_flows()` 的 `DEMO_FLOW` 补上声明；
- 发布门禁：`flow_field_errors()` 要求凡是出现在 `required_fields` 里、名字命中常见
  敏感词（`id_card` / `phone` / `bank` / `address` 等）却没有在 `sensitive_fields`
  声明的，**拒绝发布**——不靠人记得。

**不做**：

- 不改打码算法落在服务端还是页面（本 issue 只提供标记，打码在 #2）；
- 不做字段级校验（长度、格式），那是独立议题；
- 不改 `input_text` 是否落库，见"待确认"。

### 验收标准

- [ ] 正常路径：`GET /api/tasks/{id}` 返回 `flow_title="报修"`，`sensitive_fields=["contact"]`；
- [ ] 缺参/歧义：流程版本库里查不到时，两项都为空且接口不 500（对齐
      `test_task_view_survives_flow_version_missing_from_registry`）；
- [ ] 失败/超时：无新增外部依赖，不适用；
- [ ] 取消/重试/恢复：不影响任何写入路径，刷新后两项仍一致；
- [ ] 不应发生：
      - `required_fields` 含敏感名却未声明敏感 → 发布被拒（新增负向测试）；
      - 声明了 `sensitive_fields` 里不存在的字段 → 发布被拒（防笔误静默失效）；
      - `TaskView` 里出现 `input_text` 或任何原始自然语言（守住 §7 最小化）。

### 验证计划

- `pytest tests/test_web_ui.py tests/test_flow_publish.py`（若存在）与全量 `pytest`；
- 新增 `tests/test_flow_sensitive_fields.py`：声明覆盖、漏声明拒绝、笔误拒绝；
- 手工：`curl` 一次 `GET /api/tasks/{id}` 核对两项字段。

### 待确认问题与依赖

1. **敏感词表**由谁定口径（身份证、手机号、银行卡之外还有哪些？住址算不算？）；
2. 漏声明就走**拒绝发布**是否太硬——替代方案是允许发布但页面强制全部打码；
3. `input_text` 是否落库：本 issue 刻意不碰，见 #3 的"开场气泡"方案。

## Issue 2：`[功能] 群众侧对话记录：由 TaskView 派生 transcript（纯函数）`

- **标签**：`type:feature`
- **风险**：中（会话、任务状态展示；不产生写入）
- **阻塞**：依赖 #1；被 #3 依赖
- **影响范围**：涉及个人信息或敏感数据；涉及群众侧 UI

### 用户问题与预期结果

现在页面没有"对话记录"这回事：`main.ts` 的 `render()` 每次都 `replaceChildren()`
重建，群众只看到当前一屏，说过的话、助手问过什么全部消失。原型评审确认群众端定位
是对话式智能体，因此页面需要有连续的消息流。

关键约束：消息流**必须由服务端视图派生**，不能是本地累积的数组。否则 SSE 提醒、
重连、刷新都会造成重复或丢失，而"页面自己记着进度"正是这套架构一直在防的东西。

完成后：`state_view.ts` 导出 `transcriptOf(view: TaskView | null): Message[]`，
12 个状态各自的投影有明确规则且可被 Node 直接回归。

### 范围与非目标

**做**：

- 新增 `Message` 类型与 `transcriptOf`，签名与 `screenOf` 同级（纯函数、不 import 任何东西、
  不碰时钟）；
- 消息 `id` 由 `(state, step_id, 字段名)` 决定，**稳定**——重渲染不重播、不闪烁，
  DOM diff 才有依据（#3 要用）；
- 消息 `kind` 至少覆盖：`assistant`（服务端 `ui_title`/`ui_hint`/步骤 `prompt` 原话）、
  `field_question`（字段标签 + 是否已填）、`user_answer`（打码后的值）、
  `confirmation`（动作 + 关键字段 + 影响）、`result`（结果行）、`status`（失败/待确认/转人工）；
- 打码：用 #1 的 `sensitive_fields`，规则与原型一致（长度 ≥ 12 保留前 6 后 4，其余
  全掩码）；**页面不维护字段名黑名单**；
- `outcome_unconfirmed` / `handoff` / `failed` 的消息必须表达"未确认/已转人工/未成功"，
  且 `terminal` 后不再追加任何"进行中"性质的尾巴；
- 校验失败（服务端 422）时的用户原文保留：以 `rejected` 标记的消息承载，
  `id` 含尝试序号，避免同名覆盖（DESIGN §4.3）。

**不做**：

- 不发起任何请求、不改 `screenOf` 既有派生结果（新增而非替换）；
- 不做附件消息（#5）；
- 不做消息持久化、不做时间戳（页面无时钟，见 `test_projection_layer_cannot_see_time`）；
- 不做"打字中"动画（那是按等待推断状态的入口）。

### 验收标准

- [ ] 正常路径：`awaiting_input` 的有序消息 = 开场（`flow_title`）+ 已完成字段的问答对
      + 当前字段提问；`field_question` 用的是 `field_labels` 里的中文名；
- [ ] 缺参/歧义：`needs_clarification` 只出一条"没听清要办什么"的助手消息，且**不含**
      任何字段提问（服务端未建任务）；
- [ ] 失败/超时：`failed` 给出非成功措辞；`outcome_unconfirmed` 明确"结果待确认"且
      **不含**"重新提交"类消息；
- [ ] 取消/重试/恢复：同一 `TaskView` 连续调用两次 `transcriptOf`，输出深度相等
      （幂等，证明没有内部计数器）；
- [ ] 不应发生：
      - 敏感字段明文出现在任何消息里（含 `masked` 之前的中间态）；
      - 同一 `TaskView` 派生出的 `id` 集合出现重复；
      - 消息条数随调用次数增长（本地累积的典型症状）。

### 验证计划

- 扩充 `tests/test_web_ui.py` 的 `_NODE_PROBE`：导出各状态的 `transcriptOf` 形状
  （`id`/`kind`/`text`/`masked`），按上面 5 类断言；
- 新增"幂等"用例（连续两次派生结果相等）；
- 新增"敏感值不出现"用例（构造含身份证的 `slots` + `sensitive_fields`，断言明文不在输出里）；
- `ruff check .` + `pytest` 全量；`tsc` 重新构建并提交 `dist/`
  （`test_compiled_bundle_is_in_sync_with_source` 会拦）。

### 待确认问题与依赖

1. 打码保留位数是否统一 6+4（手机号会变成 `138000****0000`，可读性一般）；
2. `terminal` 之后要不要保留"已完成 N 个步骤"这类过程消息——原型保留了，但它在
   终态里属于过程信息。

## Issue 3：`[功能] 群众侧页面改为对话式：消息流 + 常驻输入框`

- **标签**：`type:feature`
- **风险**：中（会话、任务状态、群众侧 UI）
- **阻塞**：依赖 #2
- **影响范围**：涉及群众侧 UI

### 用户问题与预期结果

页面现在是"状态卡 + 表单面板"：只有 `idle` / `needs_clarification` 才有输入框，
进入 `awaiting_input` 后输入框消失、换成一个 `input` 框和"提交"按钮。群众端定位是
智能体，应该始终是一个可以说话的地方。

完成后：`web/` 页面从上到下是**消息流 + 常驻输入框**；状态变化只是往消息流里追加，
不会把输入区换掉；刷新、重连、断线都不丢对话记录（靠 #2 派生）。

### 范围与非目标

**做**：

- `index.html` 改为 `#connection` / `#notice` / `#stream` / `#composer` 骨架，
  `#composer` 常驻（输入框 + 发送）；
- `main.ts` 渲染改为：`transcriptOf(view)` → 按 `id` 复用已有 DOM 节点（新增消息追加、
  已有的不重建），避免整页闪；
- 字段回答继续走唯一通道 `/answers`（`test_compiled_bundle_is_in_sync_with_source`
  要求 `/confirm`、`/answers` 各出现一次，不能多写）；
- 确认页在消息流里以**卡片**呈现（动作 + 关键字段 + 影响三要素齐全），按钮仍在卡片内；
- 滚动：仅当用户**本来就在底部**时才自动滚到底；用户往上翻过就不抢（DESIGN §4.4）。
  判定用"距底部距离"，不用定时器；
- 焦点：提问切换后焦点落到输入框，但**不**在每次重渲染时抢焦点（否则用户正在读历史
  会被拽走）；
- 输入框随内容自动增高，且**不出现滚动条滑块**（原型评审已修过：min-height 必须
  ≥ 行高 + 边框，否则恒溢出 2px）；
- `user_action_required` 保持原有三要素与"我已完成"，不因为变成对话框而弱化。

**不做**：

- 不改任何状态语义、不新增写入动作、不碰 `presentation.py` 文案；
- 不做附件按钮（#5）；
- 不做消息时间、头像、输入中指示；
- 不做移动端专属布局重构（沿用现有响应式规则，仅核对不溢出）。

### 验收标准

- [ ] 正常路径：一句话 → 开场 + 逐字段问答 → 确认卡片 → 办结消息，全程输入框始终可见；
- [ ] 缺参/歧义：`needs_clarification` 时原话**保留在输入框里**（DESIGN §4.3），
      并给出服务端原话；
- [ ] 失败/超时：断线显示横幅且**不改**消息流；恢复后消息不重复、不丢失；
- [ ] 取消/重试/恢复：刷新页面后消息流与刷新前一致（同一 `TaskView` 派生的必然结果）；
      "重新开始"清空消息流并回到 `idle`；
- [ ] 不应发生：
      - 输入框在 `awaiting_input` 时消失；
      - 用户往上翻历史时被强制滚回底部；
      - 每次重渲染都重建全部消息节点（表现为闪烁、滚动位置跳回）；
      - 出现第二个写 `/confirm` 或 `/answers` 的入口。

### 验证计划

- Playwright 走查四场景（正常/刷新恢复/取消/断线），三视口 390·768·1200：
  `document.documentElement.scrollWidth - clientWidth == 0`、输入框
  `scrollHeight - clientHeight == 0`（无滑块）；截图留档；
- `pytest tests/test_web_ui.py`（`test_page_nodes_exist_for_every_lookup` 会核对新节点 id）；
- `ruff check .` + 全量 `pytest`；`tsc` 构建并提交 `dist/`。

### 待确认问题与依赖

1. 开场气泡文字从哪来：**建议**用 #1 的 `flow_title`（作者文案、非个人信息），
   **不**新增 `input_text` 落库。若你希望看到群众原话，需要先决定是否接受自由文本留存；
2. 确认卡片里的"修改"是否保留逐字段跳转（原型是整卡回到字段提问）。

## Issue 4：`[缺陷] 办结屏把执行器内部元数据当成结果显示`

- **标签**：`type:bug`
- **风险**：中（可能涉及结果语义与接口契约）
- **阻塞**：独立，可与 #1~#3 并行
- **影响范围**：涉及群众侧 UI；涉及个人信息（次要）

### 实际现象与期望行为

真实浏览器走查（#90 之后）在完成屏看到的是：

```text
tool=model_echo
step_id=execute_demo
text=...
trace_id=...
model_calls=1
tokens=34
duration_ms=12
stop_reason=end_turn
risk=low
```

即执行器的原始信封被逐行印给了群众。根因在 `web/src/state_view.ts` 的
`resultRows()`：它只过滤 `_` 前缀与嵌套结构，其余标量全部照发，且 `label` 直接用键名。
于是 `TaskView.result`（= `task.result`，执行器原始返回）成了群众可见信息。

期望：群众只看到流程作者声明过的结果字段与其中文名；未声明的内部字段不出现在页面。

### 复现步骤与最小复现输入

1. 启动服务，创建一个走 `demo.generic` 的任务；
2. 依次 `answers` → `confirm`，等到 `ui_state=completed`；
3. `GET /api/tasks/{id}`，`result` 含 `trace_id/tool/step_id/model_calls/tokens/duration_ms/stop_reason/risk`；
4. 打开 `/web/`，完成屏把这些键逐行印出（`tests/test_web_ui.py` 的 probe 里 `result`
   是构造数据，所以没被现有用例拦住）。

### 影响与风险

- 泄露内部实现（工具名、步号、调用与耗时），给社工与"猜接口"提供素材；
- 群众看不懂，且没有任何中文标签，等于把内部标识当结论；
- 反过来，真正的业务结果（受理编号）与内部字段混在一起，**无法判断办成没办成**——
  这已不是排版问题，是结论可信度问题。

### 防复发方案

1. 「结果能不能给群众看」由流程作者白名单决定，而不是页面黑名单
   （黑名单每加一个内部字段就要改一次前端，必然再漏）：
   - `StepDefinition` 增加 `result_fields`（有序，元素为字段名）与
     `result_labels`（可选，同 `field_labels` 的语义）；
   - `TaskView` 改下发 `result_summary: list[{name,label,value}]`，
     `result` **不再下发**给群众侧视图（内部/运营视图保留）；
   - `resultRows()` 变为照单全收（无白名单即空），并同步删掉"猜键名"的逻辑。
2. 新增回归：`tests/test_web_ui.py` 里把 probe 的 `result` 换成**真实**执行器信封形状
   （含 `trace_id` 等），断言页面上不出现这些键；`result_summary` 为空时完成屏
   只显示服务端结论文案，不显示任何原始键值。
3. 完成屏在没有 `result_summary` 时**不能**退化成打印 `result` —— 这条写进
   `web/README.md` 的走查清单。

### 风险等级

中

### 待确认问题与依赖

- `TaskView.result` 现有调用方（管理侧 `admin-ui/`、运维脚本、测试）是否依赖它？
  若要收窄群众侧，需确认改 `TaskView` 而不是新增平行视图；
- 白名单是"作者必须声明"还是"不声明就全不显示"（建议后者，安全默认）。

## Issue 5：`[功能] 输入框附件入口（➕）`

- **标签**：`type:feature`
- **风险**：**高**（文件上传、存储、隐私、副作用）
- **阻塞**：独立；建议排在 #3 之后
- **影响范围**：涉及个人信息或敏感数据；可能产生外部副作用；需要业务或安全责任人确认

### 用户问题与预期结果

原型评审要求输入框带一个 ➕ 入口（对齐 WorkBuddy 的形态），用于"拍一张、传一张"，
因为政务服务里大量材料是照片/PDF（身份证、房产证、诊断书）。

**但真实产品目前完全没有上传能力**：没有上传接口、没有存储、没有大小/类型限制、
没有保留期策略。原型里那个 ➕ 之所以在等字段时只回一句"不会上传，也不会自动填入"，
是因为它是个静态原型、不能真传——真实产品里**留一个不工作的 ➕ 就是虚假功能**。

完成后（若批准）：群众可以选图/拍照并在确认页核对待提交材料清单；不批准则本 issue
转为"不实现，改用文字说明替代"。

### 范围与非目标

**做（批准后）**：

- 上传接口：与任务/会话绑定、校验归属、限类型（`image/jpeg|png`、`application/pdf`）
  与大小（建议单文件 ≤ 8MB、单任务 ≤ 5 个）、返回不透明 `attachment_id`；
- 存储：本地受限目录或对象存储，**不进数据库**；保留期与任务一致并提供删除；
- 页面：`+` 菜单（拍照 `capture=environment` / 选图 / 选文件）、缩略图、删除、
  上传失败可重试；
- 附件只进"待提交材料"清单，**不自动填入任何字段**（原型里这条克制要保留）；
- 权限与隐私：附件不进入 `TaskView.slots`；管理侧查看需授权，记审计；
- 转人工时附件能随任务一起交接。

**不做**：

- 不做 OCR / 自动识别字段（原型也没有；那是另一条高风险链路）；
- 不做附件内容审核与病毒扫描的**实现**，但发布前必须写明"未做"这一点供业务确认；
- 不做大文件分片、断点续传。

### 验收标准

- [ ] 正常路径：选一张 ≤8MB 的 jpg → 出现缩略图与"待提交材料 1 个" → 确认页能核对 → 提交后附件归属该任务；
- [ ] 缺参/歧义：字段等待中上传，明确告知"仅作为材料，不会自动填入"，仍要求继续填当前字段；
- [ ] 失败/超时：超限/类型不符在上传前就拒绝并说明原因；上传中断可重试，不产生重复附件；
- [ ] 取消/重试/恢复：取消任务后附件按保留期清理；刷新后清单仍在（服务端为源）；
- [ ] 不应发生：
      - 未授权会话能读到别人任务的附件（必须 404，而不是 403 泄露存在性）；
      - 附件内容出现在 `TaskView` 的 `slots`/`result` 里；
      - 文件名被直接用作存储路径（路径穿越）；
      - 页面把附件 base64 塞进 JSON 请求体。

### 验证计划

- 后端：上传/归属/超限/类型/取消清理/越权 6 组用例；
- 页面：Playwright 走查选图、缩略图、删除、失败重试；
- 安全：路径穿越、超大文件、伪造 MIME 各一条负向用例；
- 如实报告"未做病毒扫描 / 未做 OCR"。

### 待确认问题与依赖

1. **是否首期做**？不做的话，输入框保持无 ➕，并在页面上说明"材料请到办理页面提交"；
2. 存储落点（本机目录 / 对象存储 / 政务云）与保留期由谁定；
3. 是否需要与既有 `harness/browser` 提交闸门共用白名单（附件域名白名单）。

## 落地记录（2026-11-09 21:00 UTC+8）

B1、B2、B3 已按顺序做完。下面只记**与原设计的差异**，逐条都写了理由。

### B1：做了与没做

| 原设计要求 | 实际 | 为什么 |
|---|---|---|
| `FlowDefinition.title` → `TaskView.flow_title` | 做了 | — |
| `StepDefinition.sensitive_fields` → `TaskView.sensitive_fields` | 做了 | 语义同 `field_labels`：逐步骤声明、按版本合并、先声明者在前 |
| 漏声明敏感词就**拒绝发布** | **没做** | 用户明确要求"先跑通流程"；且"哪几个词算敏感"是业务口径，代码替运营定会把"作者没想清楚"变成"发不出去" |
| 声明了不存在的字段就拒绝 | 做了 | 这条必须留：标错字段**看起来生效、实际没生效**，作者不会再检查一遍明文回显 |
| `demo_flows()` 补声明 | 未补 | 自检流程的 `subject` 是"办理主题"，本就不敏感；补一个空声明反而会让 `sensitive_fields: []` 看起来像是漏了 |

`flow_field_errors()` 新增的 `_sensitive_field_errors()` 只查一个方向。反方向
（`required_fields` 里像身份证的字段没被标记）**明知不做**，不是忘了。

### B2：`transcriptOf` 的实际形状

- 导出 `transcriptOf(view)`、`maskValue(value)`、`displayValue(view, name)`；
- 消息 8 类（比原设计多一类 `opening` 单列，因为它的文案规则与其他助手消息不同）；
- 打码阈值定为：`>= 12` 保前 6 后 4、`6–11` 只保后 4、`<= 4` 全掩。原设计只写了
  "长度 ≥ 12 保留前 6 后 4，其余全掩码"，照字面实现会把 11 位手机号整串掩掉——
  群众就无从确认那是不是自己那一部。这条改动记在这里，等业务口径确认；
- `displayValue()` 是**唯一**把字段值转成可显示文本的地方，`confirmation` 的摘要行
  也走它（原设计没写这一处，但漏掉它就会让确认页明文回显敏感值）。

### B3：页面骨架

- `#app` 拆成 `#stream`（消息流）+ `#panel`（状态卡与表单）+ `#composer`（常驻输入框）；
- `syncStream()` 按 `id` 复用节点，**不清空**容器：清空等于每次事件都把整段历史重播；
- 输入框整页只建一次，渲染只切禁用态与占位符，人正在敲的字与光标不会每收一条事件
  就丢一次。

### 已知边界

- 打码只对"回显"生效。`slots` 本身仍是明文（服务端语义未变），所以**浏览器开发者
  工具里能看到原值**——这是"页面不持有凭据、但确实收到了数据"的固有状态，不是这条
  改动能解决的；
- 没有做的两件事沿用原提案：`input_text` 不落库（所以开场气泡不能复述群众原话），
  消息不持久化。
